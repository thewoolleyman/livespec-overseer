## The maintainer's statement of what done means

If we already have a command CLI API surface for this, then we should absolutely use it for everything and update all of the prompts to enforce that. Do whatever we can to discourage or prevent direct writing to the file that is not type-checked and validated.

## Definition of Done assertions derived from that statement

- The overseer-declare command writes each session-writable declaration — winding-down, ready, blocked with a reason, and done with an optional summary — and clears the session's own declaration, for a worker or a supervisor entity.
- overseer-declare refuses any value that would be malformed (an empty or multi-line blocked reason, a multi-line summary, control characters, or an over-long detail): it exits non-zero naming the accepted forms and leaves the existing state file untouched.
- Every daemon-authored message that asks a session to declare (the worker and supervisor wrap-ups, the keep-going nudges, the expiry notice and the rejected-value RECOVERY line) names the overseer-declare invocation for each value, resolvable by both Claude and Codex sessions, and contains no instruction to echo into, write or delete the state file by hand.
- Each such message, and the operator documents (marker-protocol.md, the overseer operator prose and AGENTS.md), states that overseer-declare is the only sanctioned way to declare and that the state file is not to be written by hand.
- SPECIFICATION ratifies overseer-declare as the session's declaration channel in contracts.md, with a scenario that an integration test exercises.
- The fleet daemon runs a release containing all of the above, and on the installed runtime a composed wrap-up names the command while the installed command writes every value and refuses an invalid one.

## Measured starting point (master a425e55b / 0a2299c7, 2026-10-31)

- `overseer/declare.py` (console script `overseer-declare`) writes only `ready` and
  `done [summary]`, atomically, resolving the topic from `--topic`, `OVERSEER_TOPIC`, or the
  tmux pane. No `winding-down`, no `blocked`, no clear, no validation of the summary.
- Every daemon-authored declaration instruction except the final `overseer-declare ready`
  tells the session to write the file by hand:
  - `_supervisor_prompts.py` wrap-up: "Declare your state by writing ONE line…",
    `mkdir -p … && echo winding-down > {state_file}`, "removing {state_file}" to clear done,
    "write the file."
  - `_supervisor_prompts.py` / `_supervisor_prompts_nudges.py` keep-going nudge:
    `echo 'blocked: <one-line reason>' > {state_file}`, `rm {state_file}`.
  - `_supervisor_prompts_supervisor.py`: the supervisor-entity copies of all of the above.
  - `_supervisor_prompts_notices.py` expiry notice: "writing ONE line to the single state file".
  - `_signals_state.py` RECOVERY line (fix 2): "Write one of winding-down, ready, …".
  - Docs: `overseer/marker-protocol.md`, `.claude-plugin/prose/overseer.md`, `overseer/AGENTS.md`.
- Reachability: Claude sessions get `overseer-declare` on PATH from the plugin's `bin/`;
  a Codex session loads no Claude plugin, so a bare `overseer-declare` is not guaranteed to
  resolve there. The daemon's own runtime venv carries `overseer-declare` beside its
  interpreter (`~/.local/share/livespec-overseer/runtime/<sha>/venv/bin/overseer-declare`),
  so the daemon can name an absolute path that resolves for either runtime.

## Decisions (made under the standing directive; reported, not asked)

1. Extend `overseer-declare`, do not add a new surface: subcommands `winding-down`,
   `ready`, `blocked <reason…>`, `done [summary…]`, and `clear` (removes only the session's
   own declaration). Validation before any write: one line, no control characters, a
   non-empty blocked reason, bounded length; a refused value exits non-zero naming the
   accepted forms and leaves the existing file untouched. The command can never write a
   malformed value.
2. Every daemon message that asks for a declaration names the command for each value with
   explicit `--repo` and `--topic`, through an invocation that resolves on both runtimes,
   and contains no instruction to echo into, write, or delete the state file by hand. Each
   says the command is the only sanctioned declaration channel.
3. Hand-written VALID values keep working (no provenance check). Refusing them would strand
   any session still holding an older prompt mid-round, and the spec deliberately never
   inspects contents beyond the token. Prevention of the harmful case is the v075 backstop:
   a malformed value is rejected, renamed aside and named back to the session. Revisit only
   if hand-writes persist after release.
4. Spec first: contracts.md §"The state file" and §"The wrap-up injection" message
   obligations ratify the command as the declaration channel (spec tier, this seat); the
   code is factory-dispatched to petri as plan children.
