# livespec-overseer — contracts

The wire-level surfaces of the supervision, account-rotation and LLM
credential-provider contracts: state declaration and restart interlocks,
injection and nudge obligations, durable stores, daemon invocation, account
publication, and the credential consumer protocol. The interactive pane's
operator command vocabulary is deliberately NOT a governed surface, per the
scope statement at the top of spec.md.

## The state file

One file per track: `<repo>/tmp/overseer/<topic>/.overseer-state`, inside the
watched repository's gitignored scratch area. Its FIRST non-empty line is the
declaration, in the grammar `<token>` or `<token>: <detail>`.

| Value | Writer | Meaning |
|---|---|---|
| `winding-down` | session | "I received the wrap-up and am wrapping up now." Written IMMEDIATELY on receipt, before anything else. |
| `ready` | session | "I am at a clean stopping point — restart me." The SOLE restart authorization. |
| `blocked: <one-line reason>` | session | "I need a human decision I cannot make myself." Surfaced with coordinates; never restarted, never keystroked. |
| `idle-with-context-left` | daemon | The daemon's own once-per-episode nudge marker. Authorizes nothing. |
| (per entity) | — | A supervisor pair member keeps its OWN state file at `<repo>/tmp/overseer/<topic>-supervisor/.overseer-state`, with the same grammar, the same writers, and the same rules as a worker's. |

The normal sequence is two writes: `winding-down` the moment the wrap-up
lands, then `ready` (or `blocked: …`) when the session actually stops.

Contract rules:

- Any value outside the table is malformed: surfaced to the operator and
  treated as NO declaration (fail-closed). It is never coerced or
  fuzzy-matched, though it does suppress the keep-going nudge — the safe
  direction for an ambiguous file.
- Beyond the token, the file's contents are never inspected — no handoff
  hash, no payload. What a session hands its successor is its own business.
- The daemon DELETES the file as it restarts the session, together with the
  round's stamp, so a declaration can never re-trigger.
- The daemon's removal of its own nudge marker fires only while the file
  still holds `idle-with-context-left` — it can never clobber a value the
  session wrote in the meantime.
- Stale-declaration voiding: this label covers two INDEPENDENT mechanisms
  with independent triggers and independent constants. Each is stated in full
  below, and neither cross-references the other's constant.
- READY-SIDE EXPIRY. A `ready` declaration that exceeds a bounded MAXIMUM AGE
  since its own modification time — thirty minutes by default, and MAY be
  configured — is EXPIRED, regardless of session activity. The daemon MUST
  NOT void a `ready` on an activity, busy, or gated observation: a `ready`
  remains armed and eligible to certify until either the restart interlock's
  own settle, busy, and identity gates authorize a restart, or this maximum
  age is exceeded, whichever comes first. The EXPIRY INSTANT is the
  DETERMINISTIC value `declaration modification time + maximum age`, computed
  from the declaration's own recorded modification time — never a separate
  wall-clock reading taken at the moment of processing.
- Expiry clears the DECLARATION ONLY. The daemon MUST delete the state file
  and MUST NOT delete the round's sidecar key, MUST NOT reset its notified
  bands, and MUST NOT otherwise close the round.
- The two steps of a `ready` expiry are ORDERED, because the two orderings
  fail in opposite directions across a crash: the daemon MUST record the
  expiry instant (per §"The restart interlock") BEFORE deleting the state
  file. A crash between them then leaves a raised floor and a surviving
  declaration, which fails closed; the reverse order leaves a deleted
  declaration and no floor, which is harmless only until the delete itself
  fails. A failed floor record MUST be surfaced to the operator and MUST NOT
  abort the delete attempt.
- Only the `ready` expiry raises the certification floor.
- A session MAY delete its own state file when spec.md §"Wind-down expiry
  on context recovery" applies — its own remaining context has recovered
  strictly above its wind-down threshold while its own prior `winding-down`
  or `ready` declaration still stands. This is the ONE case a session
  deletes its own declaration rather than the daemon deleting it. A
  session-cleared declaration raises NO certification floor and is
  distinct from the daemon-triggered ready-side expiry above: it has no
  recorded expiry instant, and it MUST NOT be treated as a floor-raising
  event by the restart interlock.
- `BLOCKED:`-SIDE VOIDING, unchanged in effect and orthogonal to the
  ready-side expiry above. A `blocked:` declaration is voided only when the
  session is observed actively GENERATING (incompatible with waiting for an
  answer) past its own two-minute grace — a session merely running a
  background command at its prompt keeps its declaration, however old, and an
  idle blocked session is never touched. This voiding likewise clears the
  DECLARATION ONLY: the daemon MUST delete the state file and MUST NOT delete
  the round's sidecar key, MUST NOT reset its notified bands, and MUST NOT
  otherwise close the round. A `blocked:` void MUST NOT raise the
  certification floor: a `blocked:` token can never certify a restart under
  any circumstances, so a floor raised on its account would be a durable
  write with no authorization consequence.
- A fresh `winding-down` acknowledgement is honored for fifteen minutes;
  past that it is stale, escalation resumes, and the track is re-reported —
  but staleness never authorizes an act.
- A declaration MUST NOT be honored for an ACT unless its file's
  canonicalized path equals that entity's canonical state path — no symlinked
  parent directories, no symlinked file — compared against an identically
  canonicalized repository root, so a legitimately symlinked checkout still
  passes. An aliased path MUST be surfaced by name and treated as NO
  declaration, so one entity's write can never satisfy another entity's
  authorization.

## The restart interlock

A restart fires ONLY when every one of these deterministic checks passes; a
SUPERVISOR topic (per `signals.topic_reserved_for_supervisor`) is
additionally subject to a fifth, topic-conditional check:

1. A CERTIFICATION FLOOR exists for the track, anchored on a USABLE round
   timestamp. The floor is the round's injection stamp; where a `ready`
   declaration has since EXPIRED, the floor is the LATER of that stamp
   and the instant of the most recent such expiry. A track with no injection
   stamp MUST fail this check whatever else its record holds — a recorded
   expiry instant WITHOUT a usable round timestamp, or a stamp or expiry
   instant present but unreadable or non-numeric, is MALFORMED: it MUST be
   surfaced by name and MUST fail the check, never resolved by falling back
   to whichever value remains usable.
2. The state file's token is exactly `ready`.
3. The state file's modification time is STRICTLY newer than the
   certification floor — proving the declaration answers this round, and
   post-dates any expiry within it, rather than answering a prior round.
   A `ready` declaration whose own age — the current instant minus its
   modification time — exceeds the maximum age MUST NOT certify under this
   precondition, whether or not its expiry has yet been durably recorded in
   the round's sidecar. This is a fail-closed backstop independent of the
   recorded-floor mechanism above: because expiry (unlike the retired
   activity-triggered voiding) is satisfiable by the SAME observation that
   also satisfies this interlock's other preconditions — an idle, settled,
   correctly identified pane — a declaration could otherwise certify in the
   single observation between exceeding its maximum age and that expiry
   being recorded. The recorded floor remains the DURABLE record of expiry
   across restarts and observations; this age check is the point-in-time
   defense against the gap before that record exists. BOTH checks apply, and
   either one failing MUST fail this precondition.
4. The session identity live at the pane matches the ROUND-OPEN identity
   recorded for that round. A differing identity MUST hold the restart and
   surface the track rather than failing silently; an identity that cannot be
   determined, and a record carrying no identity at all, MUST both be treated
   as differing — fail-closed, per spec.md §"Fail-soft posture".
5. For a SUPERVISOR topic only (per `signals.topic_reserved_for_supervisor`),
   a RESUME-ARTIFACT CERTIFICATION: either the legacy
   `plan/<topic>/supervisor-handoff.md` exists, or the migrated
   `plan/<topic>/epic.md` names the track's recorded ledger epic id and
   references the ledger-comment binder medium. This check is read-only
   and can only BLOCK a restart pending certification — it never
   authorizes one.

   When NEITHER shape certifies, the interlock further consults whether
   the topic's plan thread is archived or gone — a DIRECTORY-level
   presence test (is `plan/<topic>/` present, is `plan/archive/<topic>/`
   present, or is neither present), never a read of file content, and
   therefore not itself a further exception to the file-touch
   prohibitions above; it is the same kind of directory enumeration
   spec.md's "enumerates plan DIRECTORIES to discover tracks" already
   permits. The two outcomes:

   - Archived or gone: the block is a TERMINAL, expected condition — the
     plan thread's own lifecycle retired it. The round closes without a
     restart and without the missing-artifact wording that would
     otherwise read as an anomaly; a distinctly-named, non-blocking-facing
     condition is surfaced instead, and the row is not left to alert on
     it again.
   - A genuinely live plan directory with the binder simply absent: this
     stays the anomalous case. The check continues to BLOCK the restart
     with the missing-artifact condition, and the round stays open,
     unresolved, until a human supplies the missing artifact or
     otherwise intervenes.

Any absent, unreadable, or other-valued file fails the check.

Where both a stamp and an expiry instant exist, the LATER of the two governs,
so the comparison always fails closed. A recorded expiry instant MUST be no
earlier than the expired declaration's own modification time plus the maximum
age; under the deterministic rule of §"The state file" it is EXACTLY that sum,
computed from the declaration's own modification time rather than read from a
clock at the moment of processing. The exclusion of an expired declaration is a
property of the RECORDED floor rather than of wall-clock time, and that remains
the correct durable mechanism. It is stated as a property of the record because
the naive wall-clock form is falsifiable: a daemon that computed a
declaration's age and recorded the expiry instant from two separate readings of
a clock that is not guaranteed monotonic could, on a backward step between
them, record an expiry instant EARLIER than the modification time of the
declaration it expires, which would then satisfy its own floor. That
falsification CANNOT arise on the expiry side under the deterministic rule
above, because no second clock reading is taken; the RECORDED-floor property is
retained as the durable mechanism regardless, and precondition 3's age backstop
covers the window before that record exists.

The guarantee that one declaration MUST NEVER authorize two kills is unchanged,
and two different mechanisms carry it on two different paths. On the EXPIRY
path it rests on a disjunction: an expired declaration is excluded whenever
EITHER the state-file delete or the floor record succeeded. Both are
fail-soft storage operations under spec.md §"Fail-soft posture", so where BOTH
fail in the same observation the declaration survives with an unraised floor;
that outcome MUST be surfaced as an attention condition rather than described
as impossible. On the RESTART path the guarantee is carried by the deletion of
the round record, exactly as before — the floor is CLEARED when the round
closes — at restart, or at a recovered-round closure — not raised, and plays no
part.

A declaration is bound to the SESSION that wrote it, and the anchor for that
binding is the ROUND-OPEN identity. The daemon MUST record the identity of the
session live at the pane WHEN A ROUND IS OPENED, and at no other instant; an
expiry MUST NOT overwrite, clear, or otherwise rewrite it. That round-open
identity is the identity every certification against that round is tested
against, per precondition 4. Where an expiry is observed with a live identity
DIFFERING from the round-open identity, the daemon MUST surface the track and
MUST NOT establish a certifiable floor from that expiry: the session that would
answer it is not the session that was asked. This extends the rule below — "a
declaration authorizes the restart of the session that wrote it, never of
whatever session later occupies that pane" — whose existing test is anchored at
first observation, and which a successor's own first-seen declaration would
otherwise pass trivially. Acting on a
passed check is additionally gated on live pane evidence: a verified empty
idle input state, a settled pane (two captures compared across a short
delay), no busy signals — including no background-shell evidence — and a
positive identity check that the pane really is this track's supervised
session in this track's repository.

A standing `ready` held by precondition 4 because a DETERMINED live identity
differs from a DETERMINED round-open identity MUST be surfaced IMMEDIATELY: it
MUST become report-only attention in the SAME completed evaluation that
observes the mismatch, without waiting for the generic uncertifiable-ready
continuity floor. That floor continues to govern certification failures which
are not themselves proof that the session changed, and BOTH indeterminate
cases stay under it: a live identity that cannot be determined, and a round
record carrying no identity at all — which is a MALFORMED record under the
certification-floor rules, surfaced through that membership instead.
Precondition 4 fails closed on both by treating them as differing, but neither
is evidence of turnover and neither yields the pair of identities this
membership must report. A live successor session can legitimately write a
fresh declaration while the round still names its predecessor, and holding
THAT case behind the generic floor renders a DETERMINISTIC certification
failure as undifferentiated `danger` — which reads as the daemon having
IGNORED a `ready`, and hides the identities needed to resolve it safely. The
row and its edge-triggered alert MUST between them name the certification
failure, the ROUND-OPEN identity, the LIVE identity, and the remediation: the
standing declaration cannot authorize a restart, and the successor must
complete a newly delivered current-session round before declaring a fresh
`ready`. The daemon MUST NOT restart the track, MUST NOT void or otherwise
clear the declaration on account of the mismatch, MUST NOT paste into the
pane, and MUST NOT silently relabel the condition as ordinary `danger` — a low
remaining-context reading MUST NOT displace the certification failure as the
track's rendered status.

The restart itself guarantees:

- The pane's PROCESS is replaced in one atomic operation — never an exit
  followed by a scrape for a shell prompt. Files, worktrees, branches, and
  commits on disk all survive.
- The fresh session is launched autonomously (it does not stall on its first
  permission prompt), named after the ENTITY's derived session name, and
  handed exactly one prompt: read that entity's ledger-held plan state — the
  entries on the governed plan's ledger epic attributed to that entity, the
  worker's own for a worker and the supervisor's own for a supervisor pair
  member, both on the SAME epic and separated by attribution rather than by
  store — and follow it. The prompt MUST name the track's repository path,
  the plan's epic id, and the entity whose entries to read, all three
  LITERALLY, so a session opening with no prior context can resolve what to
  read without opening any plan-tree file; a prompt naming only a category
  is not a pointer. A track with NO recorded epic id is not respawned at
  all: the `ready` declaration is PRESERVED and the track surfaced, exactly
  as for a respawn that failed, so a declaration is never spent on a prompt
  the fresh session cannot resolve.
- Every step is a hard gate, and the two failures are NOT the same. A
  respawn that FAILED — the pane's process was never replaced — surfaces the
  failure and PRESERVES the `ready` declaration so the next cycle retries. A
  respawn that SUCCEEDED but whose fresh session is not recognized in time
  has already destroyed the predecessor, so it CONSUMES the kill
  authorization: the round is held open for submission retry only, and any
  further kill requires a genuinely fresh `ready`. One declaration MUST
  NEVER authorize two kills.
- A restart is additionally held, and the track surfaced instead, when the
  session identity observed at the pane has changed since the `ready` was
  first seen — a declaration authorizes the restart of the session that
  wrote it, never of whatever session later occupies that pane.
- A submitted-but-dropped resume is retried by re-sending the SUBMISSION
  only — recorded round-scoped so it cannot outlive its round, branched on
  the observed input-box state rather than on busy-ness, and never escalated
  to a second kill. A fresh session showing a structured gate is reported as
  waiting on a human and never keystroked, with the round held open.
- The restart never changes the track's runtime (per spec.md §"Supervised
  runtimes").

The interlock and every guarantee above apply per supervised entity, under
that entity's own key.

## The wrap-up injection

- Trigger: effective remaining context at or below the track's threshold AND
  the complete guarded-paste predicate. The threshold is the per-track override
  when set, else the daemon-wide default (50% remaining unless overridden at
  daemon launch). Claude MUST show a positively empty input box; Codex MUST show
  its structural idle-input evidence — a live prompt and statusline with no
  generating marker or picker — because Codex cannot distinguish its empty
  placeholder from typed text. This Codex divergence applies only to the
  low-context wrap-up and MUST NOT weaken the pair nudge's positively-empty
  guard. Both settle captures MUST retain the runtime-appropriate eligible input
  shape and be identical. The pane MUST NOT be generating, changing,
  sub-agent-busy, gated, runtime-reported as waiting on a human, carrying
  `blocked:` or `ready`, or carrying a fresh `winding-down`; a stale
  acknowledgement MAY resume escalation. Shell-only eligibility MUST be
  affirmative — recognized Claude registry `status=shell`, or the Codex
  descendant-shell fallback — and any unknown, conflicting, malformed, or
  unavailable authoritative status suppresses the paste. Immediately before
  paste, the daemon MUST re-read managed-pane identity, authoritative runtime
  busy evidence, declaration, gate, and eligible-input state; any change or
  unreadable input cancels the act for that tick. No-busy and affirmatively
  shell-only-busy panes can satisfy this predicate; any other busy evidence
  cannot. A certifiable `ready` takes only the restart path after its stricter
  no-busy interlock passes; an uncertifiable `ready` remains report-only and is
  not pasted into; a malformed state value remains fail-closed as no declaration.
  The `ready` exclusion applies UNIFORMLY to ANY `ready` token on disk —
  certifiable or not, background-shell evidence present or absent, whichever
  runtime — because the daemon MUST NOT keystroke over a standing declaration.
  That uniform exclusion DEPENDS on the certification floor of §"The restart
  interlock" existing: an implementation MUST NOT tighten this predicate before
  that floor is in place, because doing so removes the only route by which a
  track carrying an uncertifiable declaration currently recovers without a
  person. It leaves a residual that is a REGRESSION against shipped behavior
  for one class of track and MUST be stated rather than discovered — a
  declaration standing on a track that was never in a round, which the floor
  deliberately does not reach, is surfaced rather than healed (per spec.md
  §"Fail-soft posture").
- The injection stamp is written durably BEFORE the message is pasted, so a
  responding declaration always post-dates it.
- Escalation bands: the threshold itself, then each lower ten-percent band
  (40, 30, 20, 10). Each band fires at most once per round; notified bands
  are durable across daemon restarts; several bands crossed at once coalesce
  into one message. At 30% remaining and below the message switches from
  suggestion to insistent demand.
- Message obligations: every wrap-up names the session's live
  remaining-context percentage, the state-file path with the three writable
  values, the ledger-held plan state as the successor's durable read-first
  source, named by repository path and epic id (with the instruction to
  APPEND a ledger entry on drift, never withhold the declaration), and
  states truthfully that only a `ready` declaration restarts the session.
- Re-warns stop while a fresh `winding-down` acknowledgement stands.
- The message is delivered as ONE atomic paste followed by a verified
  submission — a payload is never typed key-by-key, and submission is
  confirmed by runtime-appropriate evidence, with a bounded number of
  retries.

## The keep-going nudge

Preconditions, ALL required: the session is cleanly idle; has been
continuously idle for at least one hour; its remaining context is above its
threshold; it is not waiting on a human; and it has made no declaration of
its own. The daemon then pastes one keep-going message and writes its own
`idle-with-context-left` marker so the episode is never re-nudged. The
message points the session back at its ledger-held plan state, tells it not
to stop above its threshold, and offers the `blocked: <reason>` escape for a
session that is actually waiting on a human. The marker clears when the
session works again; the continuous-idle clock is in-memory, so a daemon
restart only ever delays a nudge.

The nudge MUST describe the blocked declaration generically and truthfully. It
MUST NOT name a runtime, a launch mode, or an approval or sandbox policy as
inherently unable to render a structured question unless that inability is
established by CURRENT runtime evidence. A live structured gate MUST continue to
classify the pane as waiting on a human, suppressing both the nudge and the
wrap-up paste; and the ABSENCE of a gate MUST NOT be read as proof that the
session can obtain human input by some other means. The `blocked:` token, its
surfacing behavior, and its restart prohibition are unchanged by this rule.

## Durable stores

Four operator-home files, plus the per-track state file above. This section's
store rules govern only the daemon; the caam surface's last-writer-wins
publication and fail-loudly exit rules are defined in §"The account-rotation
operation", and the LLM credential-provider operation's fail-closed persistence
rules are defined in §"The LLM credential-provider operation" below. All writes
to the daemon's own stores are atomic (a complete temp file replaces the old
file, so a reader sees the old or the new content, never a partial), and
read-modify-write sequences hold an advisory lock; on a lock or storage failure
the daemon degrades and warns rather than crashing.

- **The mapping store** (`~/.livespec-overseer.jsonl`) — one JSON object per
  line, one row per assigned track. Durable keys: `topic`, `repo`, `tmux`,
  `resume`, `epic`, `pinned_session_id`, plus `ctx_threshold` ONLY when a
  per-track override is set — a row without `ctx_threshold` means "inherit
  the daemon default", and readers MUST NOT materialize the default at read
  time. The `epic` value is the plan-state locator the read-first chain
  resolves against, and it is REQUIRED for any track whose session may be
  restarted. A recorded `epic` MUST be the plan's ledger epic id as read
  from that plan's write-once metadata anchor. Where a reader substitutes an
  in-memory placeholder for an ABSENT `epic` so that downstream code has a
  value to carry, that placeholder is a READ-TIME projection and MUST NOT be
  written back into the store: absent and recorded are the only two
  persisted states, and the projection MUST NOT become a third. A row
  already carrying such a persisted placeholder MUST be treated exactly as a
  row with NO recorded `epic` — including by §"The restart interlock", which
  therefore does not respawn it, preserves its `ready` declaration, and
  surfaces the track. The mapping store MUST NOT emit a `handoff` key; a
  legacy row still carrying one is read without error and rewritten without
  it.
  `resume` remains the operator's optional per-track override of the respawn
  prompt; when it is absent the daemon derives that prompt from `repo`,
  `epic`, and the entity name. Unknown keys survive rewrites. Malformed
  lines are skipped and named, never fatal. Steady-state cycles that change
  nothing do not rewrite the store.

  A surface that writes a mapping-store row MUST validate that write BEFORE
  performing it, and MUST refuse a write that fails validation, naming the
  offending key; the store MUST be left byte-unchanged by a refused write,
  and the surface MUST NOT write a partially-corrected row. Validation is a
  predicate on the WRITE — the row as it stands before, together with the row
  as it would stand after — and NOT on the resulting row alone. It applies to
  the row being INTRODUCED OR CHANGED by that write, and MUST NOT be applied
  to a row the write merely carries along unchanged, so a pre-existing
  non-conforming row can never block unrelated maintenance of the store. A
  row carried along unchanged that does not conform MUST be surfaced per
  §"Attention surface" rather than silently rewritten or silently dropped.

  An ABSENT `epic` CONFORMS, and a write that introduces a row with no
  recorded `epic` MUST be accepted. The REQUIRED-for-restart sentence above
  states a precondition for RESTARTING a track, never a precondition for
  WRITING its row: spec.md §"Track discovery and the mapping store" and
  §"The restart interlock" together already specify the absent-epic state and
  its consequence — the track is not respawned, its `ready` declaration is
  preserved, and the track is surfaced — so refusing that write would
  contradict them. What a write MUST be refused for is REMOVING or REPLACING
  a recorded `epic` on a row that carried one, or recording an `epic` that is
  not a ledger epic id. Removing the ROW ENTIRELY is not removing its `epic`
  and is never refused on that ground — the garbage collection of rows whose
  plan has been archived or deleted, per spec.md §"Track discovery and the
  mapping store", is unaffected by this rule. Stating the predicate over the
  write rather than over
  the row is what makes that distinction expressible at all: an
  epic-stripping rewrite yields a row indistinguishable from a conforming
  never-assigned one, so a row-only predicate cannot refuse it.

  This write-side rule and the read-side rule above govern DIFFERENT
  failures — a line that is not parseable JSON, and a write whose before/after
  pair does not satisfy the contract — and neither subsumes the other.

  A row MAY additionally carry an optional `model_profile` object —
  `{harness: string, model: string, wrapper: string|null, statusline_model?: string}` — per spec.md
  §"The launch profile". A row without `model_profile` MUST behave
  exactly as a row does today. `model_profile` MUST NOT carry any key
  other than `harness`, `model`, `wrapper`, and the optional
  `statusline_model`; it MUST NOT carry an
  environment-variable blob or any secret/token value — the wrapper named
  by `wrapper` owns its own secrets. The optional `statusline_model` records
  the rendered model name captured as the track's verification baseline — the
  signal the statusline mismatch-veto reads to distinguish having read the
  verification signal and found agreement from not having read it at all, per
  spec.md §"The launch profile"; it holds a rendered model name and never
  credential material, so admitting it does not weaken the no-secret guarantee
  above. Readers MUST treat a `model_profile`
  whose `wrapper` path does not exist and is not executable, or whose
  `harness` does not match the track's detected runtime, as stale: the
  daemon MUST surface this and MUST skip the restart for that tick rather
  than launching with a guessed or default profile.
- **The round sidecar** (`~/.livespec-overseer-stamps.json`) — a JSON object
  keyed per track, each value carrying the round-open timestamp `at` (epoch
  seconds), the notified escalation `bands`, and the round-scoped
  `resume_pending` flag, plus the EXPIRY INSTANT and the ROUND-OPEN SESSION
  IDENTITY backing the certification floor of §"The restart interlock". The
  write discipline for each is part of this contract, because that is where an
  ambiguity would otherwise live: the round-open identity is written ONCE, when
  the round opens, and is never rewritten for the life of that round; the
  expiry instant MAY be raised repeatedly within the round. Opening a round
  resets its bands; the RESTART and the RECOVERED-ROUND CLOSURE each delete
  the key entirely, so no round datum — floor and identity included —
  outlives its round. Key deletion is tied to those two round-closing events
  specifically rather than to any other round event: an expired declaration
  leaves the key in place. A legacy bare-number value is still read as a round
  timestamp. A record carrying a
  round timestamp but NO identity — the legacy bare-number value included —
  MUST NOT certify anything: it fails closed rather than being read as matching
  whatever session is live.
- **The watch-set declaration** (`~/.livespec-overseer-repos.json`) — a
  document of the shape `{"repos": ["<checkout-path>", …]}`. It is a
  hand-edited operator file, so it is parsed leniently: comments and
  trailing commas are tolerated. Admission per spec.md §"The watch-set
  declaration". An absent or unparsable declaration degrades to an empty
  watch-set with a warning, never a crash.
- **The status snapshot** (`~/.livespec-overseer-status.json`) — the daemon
  MUST rewrite it atomically on each completed tick. Its governed top-level
  fields are integer `schema_version`, `daemon_instance_id`, monotonically
  increasing per-completed-tick `tick_generation`, and `written_at`; for each
  evaluated track, one row carries `topic`, `repo`, `tmux`, `runtime`,
  `status`, `note`, `ctx`, `progress_now`, `human_wait`, `round_open`, `acked`,
  `picker_open` — whether the pane is currently showing a structured picker
  gate, carried as its own field precisely so a consumer can test for a parked
  picker WITHOUT keying on `status`, which is not stable for that purpose —
  and `session_identity`, a token derived from the live session join and
  sufficient for a consumer to detect that the session behind a row changed.
  The row's `status` is the daemon's derived classification of the track, in
  the sense governed by spec.md §"The stalled-picker charter reminder"; it is
  NOT the session's state-file declaration. The status the daemon EVALUATES for
  a track is not necessarily the status it PUBLISHES on that track's row: a
  track waiting on a human whose pane shows an OPEN structured picker MUST be
  published under a picker-stall status once its capture has been unchanged
  past the bounded stall floor, while continuing to be evaluated as
  `blocked:human`. That promotion changes no underlying condition — the session
  waits on the same human, for the same reason, before and after. A consumer
  therefore MUST NOT infer from the ABSENCE of `blocked:human` on a row that
  the track is not waiting on a human; a consumer testing whether a track is
  parked on a picker MUST use `picker_open`, which exists precisely so that
  test does not depend on the status vocabulary; and a consumer that must act
  on a human-waiting track MUST treat the published `blocked:human` and
  picker-stall statuses alike for that purpose. That promotion IS the
  "picker-stall surface" and the "picker-stall status" that the NEEDS YOU
  membership paragraph below names in distinguishing itself from them: the two
  are one mechanism under two names, and this rule is the referent for both.
  Session-authored free text in `note`, including a blocked reason, MUST be
  elided and length-bounded at serialization; the snapshot MUST NOT become an
  unelided surface for session-authored text. A snapshot write failure MUST
  be contained and edge-reported and MUST NOT terminate or degrade the
  supervision loop. The snapshot is OBSERVATION-ONLY: nothing in it
  authorizes any act, and no daemon behavior may read it back as an input.
  Consumers MUST treat an absent, unreadable, or unknown-or-newer
  `schema_version` snapshot as absent, MUST NOT best-effort-parse it, and MUST
  surface that it could not be read. Staleness is detectable from
  `tick_generation` plus file mtime; a stale snapshot proves only that no
  fresh snapshot exists — it does NOT prove the daemon is down.

A start-intent record is NOT one of the operator-home files above. It is
written to the authorized operator surface's own runtime state under the
per-repository gitignored scratch area named by spec.md §"Non-interference
with tracked work", and it MUST carry the action, the target track, the
invoker, and — once the spawn resolves — its outcome. An intent record
carrying NO outcome MUST be read as an attempt that FAILED, not as work in
progress: a surface killed between issuing the spawn and returning cannot
write an outcome, so absence of one is itself the signal. It MUST NOT be
written under `plan/`, which that same section forbids the surface from
writing.

## Daemon invocation

`overseerd` runs with NO subcommands and exactly ONE option:
`--warn-percent N`, an integer from 1 to 99 — the daemon-wide default
remaining-context threshold at which the first wrap-up fires (default 50). A
per-track threshold override in the mapping store wins over it. There are
deliberately NO flags for the store, sidecar, or watch-set paths, and no
recovery or interval options: the paths are fixed by construction, and the
daemon is surface-only (per spec.md §"Surface-only startup").

- Standard output is the live state surface, re-rendered from live captures
  on every cycle (roughly every ten seconds).
- Standard error is the timestamped event history. Diagnostic lines are
  prefixed `overseer:`; operator-relevant alerts are prefixed
  `overseer[SURFACE]:`. Track-scoped alerts carry the full coordinates per
  spec.md §"Notify, never block"; daemon-level notices (a failed paste, a
  refused startup) carry none.
- Startup gates, in order: an unsupported host is refused FIRST with the
  failed precondition named (per constraints.md §"Runtime requirements");
  then the daemon refuses if any watched repository fails the gitignore
  precondition (per spec.md §"Non-interference with tracked work"); then it
  refuses if another daemon instance already holds the singleton lock for
  the same mapping store.

## Bootstrap preconditions

The two-pane bootstrap is invoked BY the operator surface from inside the
interactive pane's own session — it is not a standalone launcher and does not
start an agent session itself. It refuses, before mutating any window, when
it is not running inside the operator's agent session or when it is not
inside a tmux pane, naming the missing precondition. It splits ONLY the
invoking window — never targeting another session by name — and it is
idempotent: a daemon pane already present is left in place. It then adopts
already-running sessions whose registered names match active plan topics.

## Attention surface

The daemon owns and renders the MECHANICAL attention surface: the
session-liveness membership enumerated here. This surface MUST remain
authoritative, self-refreshing, and complete on its own terms. A consuming
operator surface MAY compose a superset attention view from the status
snapshot in §"Durable stores". Such a consumer MUST NOT suppress, filter,
re-rank, or replace the daemon's own rendering, and MUST NOT introduce any
surface that requires the daemon's rendering to be ignored. The daemon's
report-only members authorize no act regardless of who consumes them.

Mechanical attention membership is: a blocked track, a non-responding track
at the danger line, a track whose mapped session is gone, a malformed or
path-aliased state value, a restart whose resume has not yet submitted, a
supervisor pair member that disappeared while its round was open, and the
REPORT-ONLY bounded members of spec.md §"Fail-soft
posture" — a known-low track that has been unable to open a round past its
floor (naming its background-command instance where that is the evidence), a
track busy-shielded past the longer no-progress floor, a low track whose
context knowledge has gone stale, a track carrying a standing declaration
that cannot certify past its bounded floor, and a pair whose autonomous
nudge has already failed. Membership also includes three conditions arising
from the certification floor of §"The restart interlock": a track whose
state-file delete AND floor record BOTH failed in the same observation, where
surfacing, alongside the interlock's own age backstop (per precondition 3 of
§"The restart interlock"), is the remaining guard against honoring an expired
declaration; a track whose round record is MALFORMED under the
certification-floor rules; and a track whose expiry was observed under a live
identity DIFFERING from its round-open identity. All three are report-only and
MUST NOT authorize any act, like every other member. Every member carries the
same coordinates and the same edge-triggering; the report-only members MUST NOT authorize any act. A
supervisor pair member needs no membership entry of its own — as a
supervised entity it enters attention through the same statuses as any
other. Discovered-but-unassigned plans are deliberately NOT attention —
startable is not stuck. The attention count is also badged onto the daemon's
window name, and the badge MUST clear when the count returns to zero — an
indicator that can only be set is one more stale surface.

Membership also includes an ESCALATION-EXHAUSTED track: a DELIVERED round
whose track's effective remaining context is KNOWN, not stale, and at or
below its wind-down threshold, where every escalation band at or above that
effective context is already notified, no declaration is on file, no resume
submission is pending, no generating, sub-agent, or recognized
background-shell evidence is present, and the session has satisfied its
runtime's idle predicate — a positively empty input box for Claude, the
structural idle-input evidence for Codex — continuously past a ten-minute
floor, an observation gap restarting the floor per the ratified floor rules.
An unknown or stale context reading MUST NOT establish membership. This
member is REPORT-ONLY with normal coordinates; it participates in the NEEDS
YOU count and window badge, is edge-triggered like every other member,
clears when any of its conditions ceases, and MUST NOT authorize any act — a
fresh session-written ready remains the sole restart authorization. Its
rendered note MUST state that the runtime's own idle indicator is an
input-state display and that the restart authorization — the state file
containing exactly ready — is absent, naming the state-file path. The
membership deliberately covers ANY delivered-round track idling undeclared
past the floor, not only a round whose every band is consumed: an undeclared
post-wrap-up idle session is itself the reportable condition.

Membership also includes a successfully restarted fresh session with no
observed context consumption and an exact expected resume payload still in
its composer continuously past the 60-second floor, including the case where
`resume_pending` was not recorded. This is a distinct report-only member with
normal coordinates; it participates in the NEEDS YOU count and window badge,
is edge-triggered, and authorizes no act. The SAME evidence — no observed
context consumption, no busy evidence, and an exact expected resume payload
still in the composer — does, however, independently authorize the
submission-only self-heal of spec.md §"The restart": recording the
round-scoped `resume_pending` retry and re-sending the submission only, on any
acting tick and without waiting for the 60-second floor. All three legs are
required for that authorization, and a fresh session showing a structured gate
is reported rather than keystroked. That authorization stands ALONGSIDE this
membership rather than replacing it, and it is not an exception to the
report-only rule: the self-heal never re-pastes, respawns, terminates the
session, or writes a declaration, and a fresh session-written `ready` remains
the sole restart authorization. Discovered-but-unassigned tracks remain
outside this membership.

Membership also includes a tracked session whose row reports an OPEN PICKER
and whose pane shows an inbound cross-session message queued, and still
unconsumed, behind that picker. This is a distinct report-only member with
normal coordinates; it participates in the NEEDS YOU count and window badge,
is edge-triggered, clears when the picker resolves or the queued message is
consumed, and authorizes no act. Its rendered note MUST name the sender where
the pane makes that available, so a parked delivery can be attributed without
reading the pane. This membership MUST be keyed on the picker being open and
MUST NOT be keyed on any particular row status: a session parked on a picker
may report a picker-stall status rather than a human-blocked one, so a
status-keyed condition would miss the case this membership exists to catch.
It is a distinct condition from the picker-stall surface, which is keyed on
the age of an open picker alone and reports nothing about what is queued
behind it.

Membership also includes a track carrying a STANDING ROUND WHOSE WRAP-UP WAS
NEVER DELIVERED: a round whose opening wrap-up paste FAILED and whose required
un-open — the deletion of the injection stamp the daemon had just written, per
spec.md §"The supervision round" — ALSO failed in the same observation, so the
round's durable record remains with no wrap-up behind it. Surfacing is the
remaining guard here, exactly as it is for the expiry-path double failure: once
the rollback write is lost, nothing left in the data distinguishes this round
from a legitimate one, and a declaration written afterwards would certify
against it. Membership MUST require BOTH failures in the SAME observation. A
failed opening paste whose un-open SUCCEEDED leaves the track un-rounded and
MUST NOT establish membership, and the paste failure alone MUST NOT establish
it either — that failure is already answered by the un-open and by the daemon's
own retry, and a member keyed on it would fire on the ordinary, harmless case
while reporting nothing about the hazardous one. This member is REPORT-ONLY
with normal coordinates; it participates in the NEEDS YOU count and window
badge, is edge-triggered like every other member, clears when the round's
wrap-up is subsequently delivered or when the round's durable record is
removed, and MUST NOT authorize any act — a fresh session-written `ready`
remains the sole restart authorization. Its rendered note MUST state that no
wrap-up was delivered for the standing round, so an operator can distinguish it
from a delivered round legitimately awaiting a declaration.

## The account-rotation operation

**Pi package discovery.** Repository-root `package.json` MUST be regular UTF-8 JSON whose `pi.skills` value is exactly `["./.claude-plugin/.pi-plugin/skills"]`, so Pi discovers the namespaced bindings required by both operator operations. Its package version remains outside operation-version lockstep.

**Surfaces.** In this repository, supported harness is the closed shipped set consisting of Claude, Codex and namespaced Pi bindings. The `.livespec.jsonc` `harnesses` declaration covers the Claude and Codex plugin-resolution checks only; Pi support is instead established by the required namespaced binding and package metadata and is outside that declaration. `caam-anthropic-loop` is the identity-only account-rotation operation. It MUST be constituted as a first-class plugin operation with one visible binding per supported harness. Plugin manifest versions MUST be bumped in lockstep across every manifest that declares the operation, so availability and version agree across supported harnesses.

Throughout the operator-surface contracts, “manifest that declares the operation” means exactly `<plugin-root>/plugin.json` and `<plugin-root>/.codex-plugin/plugin.json`; their name, version and description MUST remain equal. The repository-root `package.json` advertises namespaced Pi skill paths through `pi.skills`, but its package version is not an operation version and is excluded from manifest lockstep. Pi operation availability and version derive from the namespaced binding's existence plus the outer plugin manifest.

**Schedule.** The operation MUST establish its own recurring schedule and MUST check for an existing schedule before creating one, so that a scheduled invocation cannot breed a duplicate. An existing schedule whose prompt lacks the scheduled marker MUST be replaced with one that carries it. The operation MUST NOT be wrapped in a generic looping facility, which would produce a second overlapping schedule. On establishing a schedule the operation MUST disclose its identifier, its interval, that it survives only while the establishing session remains open, that it expires after a bounded period, and how to cancel it.

**Mode resolution.** An invocation carrying the scheduled marker MUST respect the rotation triggers. An invocation without it MUST be treated as an explicit request to rotate now and MUST bypass the triggers, while still refusing any move that would lose headroom and still refusing an exhausted destination. Marking the scheduled side rather than the manual side is deliberate: a lost marker MUST degrade to forcing a rotation, which is observable, rather than to never forcing one, which is silent.

**Reporting.** The caller MUST present the operation's account table to the operator verbatim and MUST NOT summarize or paraphrase its figures. On a reported failure the caller MUST surface it plainly and MUST stop; it MUST NOT retry with a relaxed threshold and MUST NOT attempt a switch by other means.

**Durable store.** The operation's cache and lock MUST live in a host state directory created with owner-only permissions, and the state file MUST be written atomically with owner-only permissions. Concurrent writers MAY overwrite one another, which MUST cost at most a cached reading and MUST NOT be able to corrupt the file. The lock MUST guard the decision, not the credential write, which the account manager already performs atomically.

**Published selection record.** The record required by spec.md §"Account rotation and quota supervision" MUST live in the same host state directory as the operation's durable store, MUST be created with owner-only permissions, and MUST be written atomically, so that a consumer reading it concurrently observes either the previous publication or the new one and never a partial file. It MUST be a separate artifact from the operation's cache: a consumer MUST NOT be required to parse operation state to learn the selection, and a change to the cache's internal shape MUST NOT break a consumer.

The record MUST name the selected account by BOTH the account manager's profile name AND the stable account identifier defined in spec.md §"Account rotation and quota supervision" under **Identity**, which that section requires the operation to resolve on every pass that determines an active account. Neither field MAY be omitted: the profile name is what an operator declares their own credential provisioning against, and the identifier is what keeps that declaration correct across a profile rename. A pass that cannot supply both MUST NOT publish, per that section's suppression rule. The record MUST carry the time at which it was written, so that a consumer MAY treat a record older than its own tolerance as stale; the operation MUST NOT itself define that tolerance, and MUST NOT expire or delete the record on its own, since a stale identity remains the best available evidence of which account to spend. The record MUST retain exactly the profile name, stable account identifier and write time and MUST NOT contain credential material of any kind. No credential-provider request or response MAY reinterpret it as a credential reference.

The operation MUST NOT require that any consumer exist: an unread record MUST be normal and MUST NOT be reported as a fault, and the operation MUST NOT wait on, poll for, or discover consumers.

**Concurrency.** Any number of concurrent callers MUST be able to report safely, since observation is read-only. At most one MAY switch. The contract MUST record, as accepted and unfixed, that a hand-run activation takes no lock, that a decision rests on readings taken moments earlier, that schedules are not deduplicated across sessions, and that the published selection record is written outside the decision lock by every pass that does publish. The lock withholds publication only from a pass that TRIED and FAILED to take it; the identity-suppression rule above withholds independently of the lock, and nothing here licenses a publication that rule forbids. A pass that holds without contending for the lock publishes normally, so a holding pass and a switching pass MAY both write and the last writer wins — which can briefly leave the record naming the pre-switch account. This is bounded rather than corrected: the next pass converges the record, and its write time lets a consumer see how old the reading is.

**Exit contract.** A completed pass that held, reported, or switched successfully MUST exit zero. Every failure MUST exit non-zero and MUST be preceded by a clearly-marked failure line, including failures arising from unexpected exceptions, which MUST be caught at the top level rather than surfacing as an untrimmed traceback.

## The LLM credential-provider operation

This section proceeds from shared cross-cutting safety rules to the external surface, privilege boundaries, configuration, acquisition, persistence, provisioning, attention and coexistence protocols. Each third-level heading is a navigation boundary; later clauses cite the one authoritative definition rather than establishing a second copy.

### Shared lifecycle terminology

`Active lifecycle state` and an operation's `matching active state` have exactly the meanings defined beside the lifecycle table in spec.md §"LLM provider credential management"; no other lifecycle status is active for worker ownership or terminal reconciliation.

### Attention-expiry precedence

An attention deadline triggers worker or command-side lifecycle recovery only while the identity-matching artifact remains `pending`. If a `resolved` artifact reaches its deadline before its still-authorized worker removes it, the worker or recovery MUST remove that artifact without a lifecycle transition and let the worker continue; worker loss or the separate worker deadline still uses its normal fenced recovery.

### Runtime prerequisite closure

For the initial `onepassword` backend, the safe `/etc/machine-id` source required by the namespace-binding contract below is a base runtime prerequisite alongside Linux procfs, `/usr/bin/keyctl`, the user keyring and `op`. Its absence or wrong type, ownership, mode or content MUST return `store-unavailable` with exit `4` before the first dependent store action or substantive mutation.

### Acquisition deadline configuration

`acquisition_worker_timeout_seconds` MUST be at least three times `provider_probe_timeout_seconds` plus six times `external_call_timeout_seconds` plus three seconds, reserving all three possible validation probes, their one- and two-second waits, browser-control startup and terminal store/lock work. A configuration that violates this cross-field relation MUST return `invalid-request` with exit `2` before store, health-adapter, acquisition-browser or provisioning-target access.

### Recovery precedence

In every rule below, not-live worker-record reconciliation that rewrites an owning launch operation to its `recovery` phase applies only after that operation's initial lifecycle conditional transition committed. When the transition did not commit, the launch-abandonment rule under launch serialization is the exclusive recovery path: it removes the pre-lifecycle operation and any orphan worker record directly, without a recovery-phase rewrite or lifecycle change.

For assignment expiration, a command “finds an expired committed assignment” before ownership or reuse validation when the assignment is expired at the mandatory assignment-expiration recovery step that precedes global mandatory recovery. A report, complete or release command that finds its assignment live at that step MUST NOT create an `expire` operation solely because global recovery crosses `lease_expires_at`; the requested command MUST close the assignment itself using its accepted time and `normalized_close_time`. Other commands that first find the assignment expired during their post-recovery stateful validation MUST apply the internal expiration rule below before ownership or reuse validation.

### Acquire uniqueness failure closure

An authoritative metadata identity lookup under the acquired provider-account lock that receives any invalid-chain descriptor cannot prove a new identity absent and MUST return `store-unavailable` before generating a `record_id`, creating an acquire operation or writing a credential. This acquire-only fail-closed rule MUST NOT make unrelated valid records ineligible for selection or other record-addressed commands.

### Explicit suspect replacement

A direct acquire matching a `suspect` record is an explicit exception to the non-dead duplicate refusal below. It MUST retain the existing `record_id`, generate a fresh `next_value_generation`, persist and run only the internal `reacquire` operation, and transition `suspect` to `reacquiring` with the same held-worker ordering and terminal behavior as dead-record reacquisition. Provision-triggered replacement retains its dead-record-only rule; only an explicit operator acquire may choose to replace a persistently suspect credential.

### Secret-store privileges

A `SecretStore` is the manager's replaceable secret backend. Every conditional record write MUST carry the complete expected logical record or expected absence, the complete desired record and the effect's `effect_id`. Under the owner-only per-record lock, the backend adapter MUST enforce that comparison through the append-only logical-revision protocol below; no mutable 1Password item update or title-uniqueness assumption may implement the condition. The manager MUST use two distinct least-privilege instances: an acquisition-secrets store containing provider login material and verification-mailbox read-only authorization, readable only by the acquisition-prerequisite checker, trusted local account-identity inspector, browser-control service's startup login-identifier resolution and local login and mailbox tools; and a provisionable-token store whose metadata is writable by acquisition, lifecycle, report and recovery writers, whose stored raw values are written by acquisition and later read only by the provider observer and final provisioning adapter. Before storage, a captured value may be held only by the browser-control service's local-tool and acquisition-validator boundaries and transferred directly to the acquisition writer as defined below. The selection brain is the least-privilege component that evaluates record eligibility and chooses one record for a request. It MUST have read-only metadata access, MUST NOT be authorized to read raw token values, provider passwords or verification-mailbox authorization, and backend credentials MUST remain outside agent context. The required initial backend is `OnePasswordSecretStore`. Throughout this operation, global recovery "expires credentials" means the following complete sequence for each eligible record: under the declared serialization it MUST first fence and reconcile any live revalidation worker, authoritatively reread the credential after that reconciliation, append the operation-less expiry audit and conditionally transition the still-expired current generation from `valid`, `suspect` or `revalidating` to `dead`. After mandatory recovery, a target request whose run has a matching nonterminal provision operation, prepared assignment, committed assignment or retained tombstone MUST return `invalid-request` without an adapter call or further state mutation and MUST NOT return its old target reference, regardless of issuance expiry. Otherwise, a retry with the same run and adapter MUST return the existing unexpired issuance and MUST NOT require the consumed registration; a different adapter for that run MUST return `invalid-request`. A matching expired issuance that remains unbound under the four-state definition below MUST instead return `invalid-request` with exit `2`, retain that issuance as the run's non-reissuable identity record, perform no adapter call or state mutation and ignore any later registration for that run; neither the same nor a different adapter may issue another reference for it. An expired registration with no issuance MUST be removed without issuing a reference.

### Purpose reservations

Configuration MUST encode `account_reservations` exactly as `{"<provider>":{"<account_id>":["<purpose>",...]}}`, where every key is non-empty and each value is a non-empty array of unique non-empty purposes. The account key uses the same identifier namespace as a provisionable record's `account_id` and selection compares them byte-for-byte; a well-shaped key with no matching record is harmless and reserves nothing. A matching account entry permits only the listed purposes; an account absent from its provider object is unreserved. The default MUST be an empty object, meaning no account reservation. If any one account's array contains more than one purpose, `health_strategy` MUST be `remaining-percent` and every registered credential-kind row for that provider MUST declare a shared-usage observer, so a shared factory/interactive reservation cannot allocate the account without enforcing its configured capacity floor. An empty purpose array, malformed shape, multi-purpose reservation under `none`, or multi-purpose reservation for a provider with a registered unsupported row MUST return `invalid-request` with exit `2` before any store or target access. This `account_id` is the credential record field, not authority derived from the separate caam published-selection record.

### Health strategies

`health_strategy` MUST be exactly `none` or `remaining-percent`. In this operation, `provider health adapter`, a registry row's shared-usage `observer` and the `provider observer` for health all mean the same registered shared-usage implementation, invoked only inside the `provider-observer` credential role in `health` mode; no separate health process or privilege path exists. Every provider-registry row MUST declare shared-usage observation either `unsupported` or as one such registered observer whose closed wire request and reduction are defined by that adapter. Under `none`, selection MUST NOT invoke a provider health adapter and MUST apply no health-based exclusion. A provisioning request under `remaining-percent` whose matching provider-and-kind row declares `unsupported` MUST return `invalid-request` with exit `2` before recovery or any store, health-adapter or target access. For a supported row under `remaining-percent`, the registered provider observer MUST resolve the candidate record's current `value_ref` outside the selection brain and reduce all provider usage windows that constrain the account to one integer shared-usage remainder from `0` through `100`; an unavailable, malformed or lower-than-`health_floor_percent` result MUST make that account ineligible, and no raw value may enter the selection process or observer output. The configured floor is inclusive, so a result equal to it remains eligible. No other health strategy or provider-health result shape MAY be accepted. The initial `anthropic` / `claude-code-oauth` setup-token row MUST declare `unsupported` because that value receives HTTP `403` from Anthropic's usage endpoint; the manager MUST NOT issue that request with the setup token or claim an observed remainder for it.

Every individual `SecretStore`, provider-health and `ProvisioningTarget` adapter call MUST have a deadline of manager time immediately before that individual call plus `external_call_timeout_seconds`. A foreground-command `SecretStore` deadline is `store-unavailable` unless authoritative conditional-write reconciliation below proves the requested replacement committed, except where the provider-observer health or revalidation, final-provisioning or detached-worker rules define their narrower outcome; a provider-health deadline makes that account ineligible; and a target-issuance deadline is `store-unavailable`. On the ordinary provision path, a target write or commit-status deadline MUST return `retryable-exhaustion`, retain its prepared assignment and lease, and require an identical retry to query commit status before any cleanup, selection or repeated write. A target-write child already launched at that deadline MUST continue while retaining the target-reference lock, but MUST reach terminal exit and release that lock no later than the original call deadline plus one additional `external_call_timeout_seconds`; it MUST perform no unbounded internal call and MUST abort before target commit if it cannot enter the evidence-and-target critical sequence by the original call deadline. The timed-out caller MUST ignore its eventual result message, but its already-authorized target and evidence transaction MAY finish within the terminal-exit bound after entering the critical sequence by the original call deadline, and the identical retry MUST observe it only after the child releases the lock. After an unexpected internal bug where target write may have begun, a commit-status deadline is instead an unavailable status result and MUST follow the later `internal-bug` fencing rule. Every other late adapter result after its deadline MUST be ignored and MUST NOT mutate manager state. The provider validation probe retains its separate `provider_probe_timeout_seconds` deadline.

Because `provider-observer` composes a values-vault read and one provider call inside one launcher role, its parent hard deadline MUST budget both operations rather than apply one SecretStore interval to the composite. In health mode the hard deadline is manager time immediately before role launch plus two times `external_call_timeout_seconds`; the internal value read and provider-health call each retain their own interval measured immediately before that individual call and capped by the composite deadline. In revalidate mode the hard deadline is the earlier of manager time immediately before role launch plus `external_call_timeout_seconds` plus `provider_probe_timeout_seconds` and the input `worker_deadline` minus three times `external_call_timeout_seconds`; a deadline no later than role-launch time MUST produce `inconclusive` without a value read or probe. The internal value read uses the earlier of its own external-call interval and that composite deadline. Only after that read succeeds may the role begin the probe, whose deadline MUST be the earlier of manager time then plus the input probe timeout, the composite deadline and the input worker deadline minus three external-call intervals, exactly enforcing the three terminal-publication intervals reserved by the revalidation worker-record deadline rule below. Reaching either composite hard deadline MUST terminate and reap the role, ignore a late result and apply that mode's existing unavailable-health or terminal-inconclusive mapping.

Final provisioning likewise has one composite parent hard deadline equal to manager time immediately before role launch plus two times `external_call_timeout_seconds`, budgeting one interval for the values-vault read and one for target validation and write. The role MUST cap each internal call by both its own interval and that composite deadline. For every target-write child rule, `original call deadline` means this composite deadline: if the parent reaches it without a conforming terminal result, the outcome is ambiguous, it MUST preserve the prepared assignment and lease and return `retryable-exhaustion`, and the child MUST terminate and release its target-reference lock no later than that composite deadline plus one further external-call interval. The child MUST abort before target commit when it cannot enter the evidence-and-target critical sequence by the composite deadline.

### Selection state

The manager MUST atomically maintain owner-only `<manager-state>/selection-state.json` containing exactly `version` (integer `1`), `incumbents` and `last_assignments`. Each `incumbents` entry MUST contain exactly non-empty `provider`, `kind` and `purpose`, lowercase RFC 4122 UUIDv4 `record_id` and UTC RFC 3339-second `target_committed_at`, be unique by the three-field `provider`, `kind`, `purpose` key and appear in lexical order by that tuple. Each `last_assignments` entry MUST contain exactly lowercase RFC 4122 UUIDv4 `record_id` and UTC RFC 3339-second `assigned_at`, be unique by `record_id` and appear in lexical `record_id` order. An absent file MUST mean the initial object `{"version":1,"incumbents":[],"last_assignments":[]}`. A malformed, non-regular, symlinked, incorrectly owned or more-broadly-accessible file MUST return `store-unavailable` with exit `4` and MUST NOT be reset or mutated. Every target commit MUST set its record's assignment time to the later of stored `assigned_at` and that assignment's `target_committed_at`. A `consume-first` target commit MUST replace the incumbent for its provider, kind and purpose only when the tuple of its `target_committed_at` and `record_id` is lexically later than the stored tuple, including when the prior incumbent was leased or ineligible; this makes delayed post-commit recovery unable to regress newer selection state. A `spread` commit MUST leave every incumbent unchanged. An assignment time MUST remain while its credential record exists even after assignment-tombstone deletion. The initial manager MUST retain every credential record and values item; credential garbage collection is not permitted, so lifecycle expiry requires only its audited conditional metadata transition. A live credential with no entry sorts as never assigned under spec.md.

When acquisition starts, the complete-record acquisition entry point under `LPM_ACQUISITION_OP_SERVICE_ACCOUNT_TOKEN` MUST atomically create the initial complete `acquiring` metadata record with its five immutable identity fields, `acquired_at` equal to the operation's `accepted_at`, null expiry, null `last_validated`, null `value_generation`, null `value_ref` and null `previous_value_ref`, and MUST append the required audit entry. Each new acquire or reacquire operation MUST generate one lowercase RFC 4122 UUIDv4 `next_value_generation` in its write-ahead input. On terminal success, the browser-control service's acquisition-validator boundary MUST capture `validated_at` as manager time immediately after the definitive provider-validation response, run the registered expiry extractor while that service still holds the capture, and return only the closed success result containing that canonical `validated_at` and nullable canonical extracted `expires_at`. Immediately after receiving that result, the worker MUST capture a publication-time candidate and set `published_at` to the later of that manager time and stored `validated_at`; a backward wall-clock step therefore clamps publication to validation rather than producing an invalid terminal shape. It MUST validate the extracted `expires_at` against normalized `published_at`. A non-null extracted expiry not later than `published_at` MUST destroy the capture, persist the exact acquisition failure terminal result with all three timestamp fields null, become terminal `failed/flow-unavailable` and follow the lifecycle transition to `dead`; it MUST NOT clamp or publish the expiry or create a value item. Otherwise the worker MUST persist `validated_at`, `published_at` and nullable `expires_at` in the operation's success terminal result before any terminal effect. The same complete-record entry point MUST then first create that generation's immutable value item, then conditionally replace the complete metadata record, set `acquired_at` to the stored `published_at`, set `expires_at` to the stored extracted value, set `last_validated` to the stored `validated_at`, set `status` to `valid`, set `value_generation` to `next_value_generation`, construct its generation-bearing `value_ref` and roll the prior `value_ref` into `previous_value_ref`. Each registered credential-kind acquisition adapter MUST also define an expiry extractor; the initial `anthropic` / `claude-code-oauth` adapter MUST produce null because `claude setup-token` provides no trusted expiry claim, while a future extractor MUST produce either one canonical expiry later than stored `published_at` or null. Reacquisition terminal success MUST replace both `acquired_at` and `expires_at` through that entry point. Every other transition, including reacquisition launch and every acquisition or reacquisition terminal failure, MUST use the distinct lifecycle conditional-set entry point under `LPM_METADATA_WRITER_OP_SERVICE_ACCOUNT_TOKEN`, limited to `status` and `last_validated`. The lifecycle writer MUST NOT read acquisition secrets or raw token values and MUST NOT write credential identity fields, `acquired_at`, `expires_at`, `value_generation`, `value_ref` or `previous_value_ref`; its writes remain store writes and MUST produce the audit entry required below. Neither writer capability widens the selection brain's authority.

Every acquisition, reacquisition and revalidation worker MUST have one atomic, regular, non-symlink mode-`0600` worker record at `<manager-state>/workers/<sha256>.json`, where `<sha256>` is the lowercase SHA-256 hex digest of the UTF-8 `record_id`. It MUST contain exactly `version` (integer `1`), lowercase RFC 4122 UUIDv4 `record_id`, `operation` (`acquisition`, `reacquisition` or `revalidation`), positive integer `worker_pid`, non-negative integer `worker_start_ticks`, Boolean `revoked`, UTC RFC 3339-second `started_at` and `deadline`; a new record MUST set `revoked` false. A revalidation record MUST set `deadline` to `started_at` plus `provider_probe_timeout_seconds` plus six times `external_call_timeout_seconds`, reserving two intervals for launch audit-lock wait and conditional metadata publication, one for the provider-observer value read, and three for terminal credential-lock wait, audit-lock wait and conditional metadata publication; acquisition and reacquisition MUST set it to `started_at` plus `acquisition_worker_timeout_seconds`. A browser-attention artifact MUST set its `deadline` to the earlier of its `raised_at` plus `browser_attention_wait_seconds` and its worker record's `deadline`. A worker or attention deadline has passed exactly when the captured manager time is at or after that `deadline`; equality therefore requires recovery. `worker_start_ticks` is Linux `/proc/<worker_pid>/stat` field 22 captured at worker start. The recorded process is live exactly when that proc record exists and its field 22 still equals the stored value, preventing process-id reuse from impersonating it. The worker is authorized exactly while that process is live, `revoked` is false and the current time is strictly earlier than `deadline`. A missing, malformed, broadly accessible, symlinked or non-matching worker record for an active worker state MUST be treated as not live. Mandatory global recovery MUST enumerate every nonterminal acquire, reacquire and revalidate operation even when no worker record exists. After recovery acquires the launch serialization defined below, a `launch` operation whose `worker-record-create` is incomplete and whose worker path is absent, or whose worker record is absent while no matching active lifecycle state exists, MUST be removed without a lifecycle change; it MUST NOT block or be resumed as a worker launch.

From before persisting a `launch` operation through worker-record persistence, the initial lifecycle conditional transition and worker release or failed-launch cleanup, an acquire or reacquire launcher MUST continuously hold its provider-account lock and a revalidation launcher MUST continuously hold the credential-record lock for that `record_id`; these are that operation's launch serialization. Before recovery classifies any pre-lifecycle `launch` as abandoned, it MUST try that launch serialization with `LOCK_NB`. Contention proves only that a launcher may still be in flight: recovery MUST leave the operation and any worker record unchanged, continue recovery of other records and MUST NOT treat the contended operation as an error or resume it. Only a recovery actor that acquires the serialization may apply the absent-or-not-live removal rule, and it MUST hold that lock through the authoritative reread and conditional removal. Thus the interval between operation persistence, held-worker spawn and worker-record creation cannot be mistaken for launcher death.

Starting any such operation MUST first spawn its worker in a held state in which it performs no provider or store action, then persist the complete worker record, then compare-and-set the corresponding lifecycle transition conditioned on that complete worker record still being present, and only then release the worker. The held worker MUST exit without acting if its launcher dies before release. If worker-record persistence fails, lifecycle audit prevents the conditional mutation, or lifecycle persistence is definitively uncommitted, the launcher MUST terminate the held worker and remove any orphan worker record; no new active lifecycle state may then be visible. A launch conditional-set that returns a definitive `condition-failed` MUST make that launch effect a definitive conditional refusal: the launcher MUST keep the worker held, set its worker record `revoked` true, terminate and reap the process group, remove that worker record and the abandoned launch operation, and leave the credential unchanged. A cleanup failure MUST retain the revoked record and operation and return `store-unavailable`. After successful cleanup, direct acquire MUST return `invalid-request`; synchronous revalidation MUST count that candidate as a non-success and continue; and provision-triggered replacement MUST return its normal `retryable-exhaustion` without claiming a launched worker. If lifecycle persistence instead has the unknown outcome defined by authoritative conditional-write reconciliation, the launcher MUST NOT release the worker: it MUST atomically set the complete worker record's `revoked` field true, terminate and reap the worker process group, retain that revoked worker record together with the owning launch operation and pending byte-identical conditional-set effect, and return `store-unavailable`. Failure to confirm termination retains the same revoked fence. A retry or later recovery MUST reconcile that exact conditional-set before any cleanup: an authoritative desired revision completes the launch effect and immediately enters the operation's failure `recovery` phase to transition the active credential to its lifecycle-table failure state before removing the worker and operation records; an unchanged expected predecessor retains or retries only the same effect under the general unknown-outcome rule; and any different authoritative revision is the pending-effect invariant failure and retains the revoked worker and operation while returning `store-unavailable`. Active lifecycle state created by an unknown launch outcome therefore remains paired with a complete matching worker record, but that safety record MAY name a revoked, ended process until recovery finishes. A new launch MAY atomically replace a worker record only after proving its recorded worker is not live and completing any owning operation reconciliation. Pre-operation recovery MUST reconcile every not-live worker record whose credential is absent or no longer occupies the active state matching that operation. With no owning operation record it MUST remove only the orphan worker record. With an owning launch operation it MUST transition that operation to its `recovery` phase and failure form. An unfinished terminal-failure operation, or a terminal-success operation whose credential conditional-set is complete or whose exact desired replacement is authoritative, MUST preserve and resume that terminal phase. An unfinished terminal-success operation lacking both forms of authoritative success MUST instead be rewritten to the operation's failure `recovery` phase with its recovery-writer effect identifiers. When another actor already changed or removed the credential, that recovery credential conditional-set MUST be a completed no-op, after which recovery removes the worker and operation records without changing the non-active credential; a later operation for the same record_id can therefore start fresh.

A live revalidation worker is matching for a provision recovery candidate exactly when it is authorized, its worker record says `revalidation`, the one nonterminal revalidate operation at the `LP(record_id)` idempotency key owns that record and is in `launch` or `terminal`, and the authoritative credential has the same `record_id`, status `revalidating` and the value generation captured by the waiting provision. Before waiting, provision MUST retain that generation and the operation fields needed to derive its terminal `credential-conditional-set` effect identifier. It MUST release every credential-record or audit-log lock needed by the worker, wait only until that worker exits or its recorded deadline is reached, reacquire released locks in the declared order, perform required deadline or not-live recovery, and reread the complete logical metadata chain without cache. The result counts as a successful candidate only when the current revision carries that captured operation's terminal conditional-set effect identifier, has status `valid`, preserves the captured value generation and stores its non-null worker-written `last_validated`; otherwise provision MUST treat it as a non-success and continue in candidate order. Two provisions that reach the same candidate therefore MUST share that one record-keyed revalidate operation: only the invocation that creates the record-keyed revalidate operation may spawn its worker, that worker's provider-observer role alone makes the single probe, and a later invocation finding the matching live worker MUST follow this bounded wait instead of spawning another. A live worker or pending operation is mismatched for this purpose when any matching condition is false. If a new direct acquire, synchronous revalidation or provision-triggered replacement would encounter any valid live worker record or nonterminal worker operation at that record's path other than the matching-wait case or the authorized-active-acquire retry defined below, it MUST NOT spawn a held worker, overwrite or remove either record, or change the credential; direct acquire MUST return `invalid-request`, synchronous revalidation MUST count that candidate as a non-success without waiting, and provision-triggered replacement MUST return `retryable-exhaustion`. If spawning the held child fails after a provision persisted a fresh revalidate `launch` operation but before `worker-record-create`, it MUST remove that empty launch operation, count the candidate as a non-success and continue in candidate order. The equivalent provision-triggered reacquire spawn failure MUST remove its empty launch operation and return `retryable-exhaustion`; neither failure changes credential lifecycle state.

Every acquisition-writer, lifecycle-writer, report and recovery mutation of one credential MUST run under the same per-record operation serialization. Each worker MUST be the leader of a new process group. An acquisition or reacquisition worker MUST hold the provider-account lock for its whole authorized lifetime and MUST hold no other inherited manager lock; a revalidation worker MUST inherit no manager lock. Every Chrome, terminal, browser-control or agent child MUST hold no manager lock descriptor, while the acquisition or reacquisition worker itself MUST retain its account lock until terminal lifecycle commit and worker-record removal. Every conditional store mutation MUST use `conditional-set`. Every worker lifecycle commit, including terminal metadata `credential-conditional-set`, MUST be a compare-and-set conditioned on BOTH the credential remaining in the operation's matching active state and the complete worker record still naming that worker's `worker_pid` and `worker_start_ticks` with `revoked` false and the current time strictly earlier than `deadline`. Immediately before `secret-value-set`, the worker MUST verify those same authorization predicates under its existing provider-account and per-record serialization; the ensuing immutable generation create is the declared unconditional set and has no `condition-failed` result. A deadline or revocation racing after that check may leave only an unreferenced generation item because the later terminal metadata compare-and-set still enforces worker authorization. Deadline or interruption recovery MUST first atomically set `revoked` true under that serialization, terminate the entire process group and confirm that no member remains, and then compare-and-set the active credential to the lifecycle table's failure state; a revoked or late worker therefore cannot commit a value or revive a recovered record. If termination cannot be confirmed, recovery MUST leave both the credential in its active state and the worker record with `revoked` true, return `store-unavailable` with exit `4` and perform no substantive command operation; every later recovery MUST retry termination and MUST NOT remove the record until the process is confirmed ended. The fenced worker MUST exit when its next compare-and-set is refused. An attention artifact whose credential is no longer `acquiring` or `reacquiring` MUST only be removed. On normal worker completion, the manager MUST commit the value and lifecycle transition first and remove the worker record second as ordered write-ahead effects. Recovery of a not-live worker whose credential is already non-active MUST follow the operation-reconciliation rule above; it MUST NOT remove a matching live held-worker record before the launcher's state transition.

### Acquisition role protocol

The acquisition worker MUST run exactly one research agent invocation followed, only when research is ready, by one or more execution agent invocations, using a general acquisition instruction rather than a provider-scripted interaction sequence. For that initial selector, header order is the order in the Gmail API message's decoded RFC 5322 header block. ### Operator acquisition protocol

`llm-provider-manager acquire --acquisition-json <path|->` MUST accept exactly one object containing `version` (integer `1`) and non-empty `provider`, `account_id`, `kind` and `purpose`; `-` means standard input, and trailing non-whitespace or any other field is malformed. The four-field identity MUST determine the acquire idempotency key and direct acquire-operation path. Before trying the non-blocking per-provider-account acquisition lock, an invocation MUST resolve that direct path and perform one read-only metadata identity lookup over canonical records; exactly one matching record supplies the `record_id` whose internal reacquire-operation path it MUST also inspect, while no match, duplicate identity or an unavailable preliminary lookup supplies no record locator and MUST NOT itself return a stateful result or be interpreted as authoritative absence. This lookup is only a locator until repeated authoritatively under the acquired account lock. Thus an identical retry can find either its direct acquire operation and generated `record_id` or the internal reacquire operation of the one matching record; no second acquire operation exists for reacquisition. Only a new identity may generate a globally unique lowercase RFC 4122 UUIDv4 `record_id`, which the caller cannot supply. If the lock try is refused because the matching active credential's own authorized acquisition worker holds it, the retry MUST emit the original active success with that `record_id` and MUST NOT recover, mutate or create state, whether the launcher has released that worker yet or not. Any other initial lock contention MUST run the global worker-recovery and one-retry branch in the account-lock recovery paragraph below and MUST return `invalid-request` with exit `2` only if that second try remains contended. After acquiring the lock, the command MUST repeat the identity lookup authoritatively and resolve an operation only from that result; duplicate identity or unavailability MUST be retained as `store-unavailable`, not treated as absence, while an exact unique result may recover or resume the one matching acquire or reacquire operation. It MUST retain any authoritative-lookup failure or recovered-operation result, complete the global mandatory recovery sequence while retaining the provider-account lock and only then return that retained result or evaluate the resulting identity state; a global-recovery failure takes its defined failure instead. This sequence is mandatory whether or not a matching operation existed. If active lifecycle state is visible but its held worker died before release, recovery MUST complete the terminal transition to `dead`, remove the worker and operation records, and return `invalid-request` identifying the failed attempt without launching replacement. The uniqueness check and initial `acquiring` record creation MUST run under that same lock. An existing non-dead record with the same `provider`, `account_id`, `kind` and `purpose` and no matching pending operation MUST return `invalid-request` with exit `2` without creating a record or worker. A matching `dead` record MUST instead keep its `record_id`, generate a fresh `next_value_generation`, persist and run only an internal `reacquire` operation, and transition `dead` to `reacquiring` using the same held-worker ordering; this is the operator path for restarting a failed or expired identity. The launcher MUST transfer the held lock to the acquisition or reacquisition worker. That worker MUST hold it while its process runs and, on the normal path, MUST exit only after its terminal lifecycle commit and worker-record removal.

When an acquire invocation begins with a matching pending acquire or reacquire operation whose worker is no longer live, it MUST complete that operation's recovery without launching a replacement in the same invocation. A recovered terminal success whose complete metadata transition committed MUST finish every remaining effect and emit exactly `{"version":1,"status":"ok","operation":"acquire","record_id":"...","credential_status":"valid"}`. A recovered terminal failure, a lost worker whose active state becomes `dead`, or a launch abandoned before active state became visible MUST finish its applicable cleanup and return `invalid-request` with exit `2`, naming only that the prior attempt failed; the next explicit acquire may then use the normal dead-record or new-identity path. Failure to complete recovery MUST return `store-unavailable` and retain its safety state. No one of these recovery outcomes may start another worker, and a later acquire with no matching operation evaluates the resulting valid duplicate or dead record normally.

After a fenced or lost acquisition or reacquisition worker process ends, recovery MUST use an account lock the current command already holds or try that lock non-blockingly. On contention it MUST leave the credential active and revoked worker record intact, return `store-unavailable` with exit `4` and perform no substantive operation. A contender that already holds the account lock while resuming the matching operation MUST complete that fenced terminal transition and worker-record removal under its existing hold before it may evaluate a new acquisition. On acquire's preliminary account-lock try, contention owned by the matching authorized active worker MUST return the original active success through the sole exception above. Any other contention MUST first run global worker recovery, including fencing and terminating a no-longer-authorized owner, and then try that account lock once more before returning a refusal; if recovery fails it returns that typed failure, if the second try remains contended it returns `invalid-request`, and if the lock is acquired it MUST hold it while completing the remaining mandatory global recovery and only then evaluate duplicate state. Every path that newly acquires a provider-account lock for acquisition or provision-triggered replacement MUST, before spawning or transferring that lock to a new worker, rescan every acquisition and reacquisition worker record for that provider account and reconcile every newly fenced or lost worker under the existing hold. This rescan closes a worker-death race after global recovery; a live conflicting worker or failed reconciliation MUST start no new worker and return the applicable contention or recovery failure. Fenced revalidation recovery MUST instead complete its transition to `suspect` under credential-record serialization alone. Provision-triggered replacement that meets any other lock contention MUST start no worker and return `retryable-exhaustion`. The command MUST use the held-worker ordering above, so the complete worker record exists before the acquisition writer makes the initial `acquiring` or `reacquiring` record visible. After both commit, it MUST release the worker to run independently of the command process and emit exactly `{"version":1,"status":"ok","operation":"acquire","record_id":"...","credential_status":"acquiring"}` for a new identity or `{"version":1,"status":"ok","operation":"acquire","record_id":"...","credential_status":"reacquiring"}` for a restarted dead identity. Malformed input MUST use the common `invalid-request` output and exit `2` without store or worker access; persistence failures MUST return `store-unavailable` and a held-worker spawn failure or other unexpected internal failure MUST return `internal-bug`. Every acquisition command input and output MUST NOT contain credential or login material.

A direct-acquire held-worker spawn failure MUST remove its empty launch operation before returning `internal-bug`; it MUST leave no worker record or credential mutation.

### Credential record

Every field named `record_id` in this operation's credential, role-input, worker, attention, fence, lease, assignment, tombstone, receipt, operation-input, selection-state, proof and consumer-message schemas MUST be a lowercase RFC 4122 UUIDv4. Each provisionable record MUST contain exactly `version` (the integer `1`); lowercase RFC 4122 UUIDv4 `record_id`; non-empty string fields `provider`, `account_id`, `kind` and `purpose`; UTC RFC 3339-second fields `acquired_at`, nullable `expires_at` and nullable `last_validated`; one lifecycle `status` named in spec.md §"LLM provider credential management"; nullable lowercase RFC 4122 UUIDv4 `value_generation`; nullable opaque `value_ref`; and nullable opaque `previous_value_ref`. Those five identity fields MUST be immutable for a given `record_id` across acquisition replacement and lifecycle writes, and `record_id` MUST be globally unique; the store MUST refuse an identity change or duplicate. `value_generation` and `value_ref` MUST both be non-null in `valid`, `suspect` and `revalidating` states and MAY both be null in `acquiring`; `dead` and `reacquiring` MUST retain both from the last value when one exists. A `valid` record MUST also carry a non-null `last_validated`. A record is age-stale when `last_validated` is null or current time is at or after `last_validated` plus the configured `maximum_validation_age_seconds`; it is expired when `expires_at` is non-null and current time is at or after `expires_at`. Once the canonical metadata envelope has parsed, a record with a missing or extra member, wrong field type or value, identity conflict, lifecycle inconsistency or invalid generation/reference relation MUST be ineligible, MUST produce a secret-free diagnostic and MUST NOT prevent another valid record from satisfying the request. Only a `valid` record that is neither age-stale nor expired MAY be selected.

A credential record with an existing pending metadata-effect fence or a nonterminal acquire, reacquire or mismatched revalidate operation MUST be ineligible for normal selection and recovery-candidate handling. The sole recovery-candidate exception is a record whose only such blocker is the exact matching authorized live revalidation worker and record-keyed operation defined above: it remains eligible for recovery-candidate discovery, and every provision that reaches it MUST enter the bounded matching-live-revalidation wait before reconsidering the authoritative record. No cache hit may bypass either exclusion or the required wait.

At rest within manager stores raw credential bytes MUST live behind `value_ref`; the consumer's isolated target is the only authorized durable copy outside that store. Within the manager-owned trust surface—the manager, workers, roles, acquisition agents and every process they spawn—raw provider credential, login and mailbox bytes MUST NOT appear in any process argument or environment, record, operation output, provisioning receipt, audit entry, proof record, log, trace, screenshot or handoff. The invoked bootstrap's inheritance of a consumer-supplied credential override is permitted only until its mandatory first-step name-only environment scrub; it MUST NOT read the value and no substantive manager process may inherit it. A service-account token has exactly two permitted environment representations during one role call: its token-bearing role process receives only the corresponding manager-named variable, and the isolated `op` child receives only `OP_SERVICE_ACCOUNT_TOKEN`; no other manager-owned process environment or environment name may contain it. After a committed provisioning write, how the consumer uses its isolated target, including a consumer-owned credential environment, belongs to that consumer's contract and is outside this prohibition. Every provisionable-token SecretStore mutation MUST first append a local audit entry naming the record, actor, attempted operation and time without a secret value. Audit entries attest adapter calls that are actually attempted; the provisionable-token store remains authoritative for whether an attempt committed. An `audit-append` ordered immediately before a provisionable-token effect MUST append exactly when that paired effect will invoke its adapter. When `secret-value-set` or `credential-conditional-set` is defined to be a completed no-op, including terminal acquisition failure, `unknown` report or replaced report generation, its paired `audit-append` MUST also be a completed no-op and MUST append no line. The audit log MUST be append-only: an existing entry MUST NOT be rewritten or removed. Every filesystem-backed local store and audit file MUST be mode `0600` beneath a mode-`0700` manager state directory; creation MUST refuse a pre-existing path with broader permissions rather than expose data.

Every audit append MUST hold the audit-log lock, read and validate the complete prior file, and atomically replace it with exactly those prior bytes followed by one canonical JSON line and newline. Before appending, it MUST scan the validated file for its `effect_id`: exactly one existing entry whose `version`, `record_id`, `effect_id`, `actor` and `operation` equal the pending append MUST count as the completed append without adding a line, regardless of that first attempt's stored `attempted_at`; a mismatching or duplicate occurrence MUST be `store-unavailable`. The writer MUST durably sync a new replacement and parent directory before marking `audit-append` complete. A crash before replacement MUST leave the prior file byte-identical; a crash after replacement MUST expose the whole new line, never a torn suffix. This prefix-preserving replacement is the audit transaction and does not rewrite or remove an existing entry.

### Persistence failures and recovery

A credential-store mutation MUST occur only after its required audit append succeeds. If the append fails, the credential-store mutation MUST NOT be attempted. If the following store mutation returns a definitive uncommitted result, credential state MUST remain unchanged and the secret-free attempted-operation audit entry MUST remain because the audit is append-only; an unavailable, deadline, interrupted or malformed result instead follows authoritative reconciliation below and MUST NOT be asserted uncommitted. A lifecycle-expiry transition that performs exactly that audit append followed by one conditional metadata mutation is exempt from creating a write-ahead operation record: the durable audit entry is its attempt evidence and the single store compare-and-set is its only substantive mutation. A persisted terminal failure fixes the worker's semantic terminal outcome before any later worker loss, so recovery MUST resume that phase with its original terminal result, effect identifiers and semantic actor. A persisted terminal success fixes success only when its `credential-conditional-set` is already marked complete or its exact desired metadata replacement is authoritative; otherwise worker loss MUST apply the terminal-success rewrite to `recovery` below. A fenced or lost worker with no persisted terminal phase MUST instead enter or resume its owning operation's `recovery` phase with the contract's failure result and recovery-writer effects. Each individual manager-local audit, lease, registration, issuance, target-commit-evidence, assignment, tombstone, proof or operation-journal transaction MUST be atomic; a command MAY require several ordered transactions.

Every `credential-conditional-set` request MUST carry the complete expected logical predecessor, which MAY be absent, the complete canonical desired replacement and the effect's `effect_id`. A deadline, interruption, unavailable transport or malformed adapter result MUST make its physical-create outcome unknown. The manager MUST terminate and reap that directly launched adapter subprocess, retain the per-record lock, bypass every cache and authoritatively reread the complete metadata revision chain before deciding the effect. An exact desired next revision carrying that effect_id proves the logical effect committed and MUST advance it without another adapter call. Only when the current invocation created the pending-effect fence from absence and that first adapter call returned an ordinary definitive result may another valid current logical record that differs from the expected predecessor prove the condition failed and follow that effect's conditional-refusal or completed-no-op rule. After an unknown result, the exact expected predecessor or expected absence proves only that no desired revision was visible by that reread; the manager MUST retain the effect and every owning operation or worker safety fence as the record's pending-effect fence and return `store-unavailable`, and a retry MAY issue only the byte-identical revision title and fields. Every call that found the fence already present MUST conservatively treat it as having a prior unknown outcome, including after a crash between fence creation and the first adapter call. Its later `uncommitted` result MUST retain the fence, and its later `condition-failed` result or different current revision MUST return `store-unavailable` without advancing or removing it. Because no different manager create may pass the fence and physical duplicates collapse, either the original or retry may create only the desired logical revision, while a late duplicate cannot conflict with, overwrite or outrank another manager revision. A failed reconciliation read likewise returns `store-unavailable` and retains that safety state. The same reconciliation MUST run for the operation-less lifecycle-expiry exception before it returns; its retained pending-effect fence MUST be discoverable by later commands even though it has no operation record.

The remaining manager-local files MUST use deterministic owner-only paths: issuance records at `<manager-state>/issuances/<sha256(LP(target_ref))>.json`, target-commit evidence at `<manager-state>/target-commits/<sha256(LP(target_ref))>.json`, leases at `<manager-state>/leases/<sha256(LP(provider) || LP(account_id))>.json`, assignments at `<manager-state>/assignments/<sha256(LP(consumer_run_id))>.json`, tombstones at `<manager-state>/tombstones/<sha256(LP(consumer_run_id))>.json`, write-ahead records at `<manager-state>/operations/<sha256(LP(command) || LP(idempotency_key))>.json`, pending metadata-effect fences at `<manager-state>/pending-metadata-effects/<sha256(LP(record_id))>.json`, and the audit log at `<manager-state>/audit.jsonl`; each path digest is lowercase SHA-256 over the displayed length-prefixed UTF-8 values, with `LP` defined above. Absence MUST mean respectively no issued reference, no target commit evidence, no lease, no assignment, no tombstone, no pending operation, no pending metadata create and an empty audit history.

A pending metadata-effect fence MUST be an atomically replaced regular non-symlink mode-`0600` file containing exactly `version` (integer `1`), lowercase RFC 4122 UUIDv4 `record_id`, lowercase SHA-256 `effect_id`, `writer_role` (`acquisition-writer`, `lifecycle-writer`, `report-writer` or `recovery-writer`), positive integer `revision`, non-empty `item_title`, lowercase SHA-256 `predecessor_sha256`, nullable complete canonical `expected_record`, complete canonical `desired_record` and nullable lowercase RFC 4122 UUIDv4 `owner_operation_id`. Its writer role MUST equal the semantic audit actor assigned to that owning operation, phase and effect by the actor table below; operation-less lifecycle expiry MUST use `recovery-writer`. Its revision, title and predecessor digest MUST equal the append-only logical-revision forms derived from those records and the effect id; `owner_operation_id` MUST equal the owning write-ahead operation or be null only for operation-less lifecycle expiry. Under the credential-record lock and before the adapter's physical-create call, every conditional-set MUST atomically create this file from absence or find it byte-identical; a different existing fence is `store-unavailable`. A definitive `condition-failed` or `uncommitted` result from the first adapter call MUST remove the fence before applying that result exactly when the current invocation created it from absence and that call had no interruption or unknown outcome. An authoritative desired revision MUST remove the fence before advancing the effect. Every unknown outcome MUST retain it; because an existing fence cannot distinguish a pre-call crash from a post-call crash, any invocation that found it already present MUST retain it on a later `uncommitted` or `condition-failed` result and apply the unknown-outcome rule above. Mandatory global recovery and every later conditional-set for that record MUST reconcile an existing fence first and MUST NOT create another revision while it remains. During global recovery, any manager command MAY launch the fence's validated `writer_role` through the closed credential-role launcher with that registry row's key description and MUST retry only the byte-identical revision through that role's original entry point, preserving the original semantic audit actor; complete-record revisions therefore use `acquisition-writer`, while the three metadata field-boundary roles use their recorded role. A malformed, unsafe or relation-invalid fence, including a writer-role mismatch, MUST return `store-unavailable` without reset or mutation.

Terminal-success pending-fence recovery is the sole exception to the broader phase-rewrite, authoritative-success and immediate-fence-removal rules. When an acquire, reacquire or revalidate terminal-success `credential-conditional-set` still owns a pending fence after its worker is revoked or not live, the operation MUST retain its original terminal phase, result and effects while that fence is unresolved; for every broader terminal-success rewrite rule, such an operation does not yet lack authoritative success and MUST NOT be rewritten. Fence relation validation MUST continue to derive the original terminal effect identifier, actor and writer role from the fence and owning operation even after the special transition below. Under the credential-record lock, recovery MUST reconcile or retry only the fence's byte-identical desired revision through its recorded writer role. That replay is exempt from the live unrevoked worker precondition solely to establish the deterministic intermediate metadata revision; it is a recovery executor action, grants the worker no authority and permits no other store mutation. When the exact desired revision becomes authoritative, recovery MUST retain the fence, atomically rewrite the owning operation directly to its failure `recovery` phase with new recovery-writer effects, and only then remove the fence before attempting the recovery conditional-set. A crash before that phase rewrite therefore leaves the original fence and terminal operation to resume; a crash after the rewrite leaves the fence related to its original terminal effect until removal and the durable recovery phase prevents terminal success. Every command discovering this state MUST complete or fail that sequence during mandatory global recovery before selection or another substantive action. A different authoritative revision, unavailable reread or unsuccessful identical retry MUST retain both fence and operation and return `store-unavailable`. This rule applies even when the desired revision was already visible on the first recovery reread, conservatively ending acquisition or reacquisition as `dead` and revalidation as `suspect` rather than preserving a success whose fence outlived its worker.

The recovery `credential-conditional-set` created by that terminal-success pending-fence rewrite is exempt from every generic completed-no-op rule for an authoritative record outside the original active state. Its complete expected predecessor MUST be the exact fenced desired revision, including the operation's `value_generation`, and its desired record MUST differ only by the recovery transition from `valid` to `dead` for acquire or reacquire or from `valid` to `suspect` for revalidate. The fence replay is the same operation's intermediate effect, not “another actor”; only a revision changed by an actor other than that replay may invoke the generic mismatch no-op.

Mandatory global recovery MUST attempt pending fences in lexical `record_id` order. A malformed fence, unavailable authoritative reread, different authoritative revision or unsuccessful identical retry MUST quarantine only that record for the current invocation, retain its fence and owning safety state, and allow recovery to continue for every other record. A requested command MUST return `store-unavailable` when its explicit or resolved record identity is quarantined. Provision MUST exclude a quarantined record; if no non-quarantined record can satisfy the requested provider, kind and purpose and at least one otherwise matching record was quarantined, it MUST return `store-unavailable` rather than `retryable-exhaustion`. A command whose result has no dependency on any quarantined record MAY continue normally. Thus an unreconcilable fence cannot globally wedge unrelated records, while no command may read, select or mutate the quarantined record as authoritative.

For every broader fence rule that says a malformed or unreconciled fence “returns `store-unavailable`”, the quarantine paragraph fixes that return's scope to a command dependent on the affected record. Attempting and quarantining the fence completes the global traversal for that record without completing or removing its pending effect.

An issuance record MUST contain exactly `version` (integer `1`), non-empty `target_ref`, `adapter` and `consumer_run_id`, absolute `isolated_root` and `target_path`, and UTC RFC 3339-second `issued_at` and `expires_at`. Its expiry applies only while no matching nonterminal provision operation, prepared assignment, committed assignment or retained tombstone binds that reference. Throughout the issuance rules, `unbound` means that all four states are absent.

The built-in adapter's target-commit evidence MUST contain exactly `version` (integer `1`), `status` (`prepared`, `armed` or `committed`), non-empty `target_ref`, `consumer_run_id`, lowercase UUIDv4 `value_generation`, lowercase SHA-256 `target_sha256`, UTC RFC 3339-second `prepared_at`, and nullable UTC RFC 3339-second `committed_at`. `committed_at` MUST be null exactly for `prepared` and non-null for `armed` and `committed`. Under the target-reference lock, the adapter MUST hash the exact credential bytes, stage and durably sync the replacement target, capture an initial manager time strictly earlier than `lease_expires_at` as `prepared_at`, and atomically persist and sync `prepared` evidence. Immediately before invoking the atomic target replacement, it MUST take a final manager-time lease-fence sample and require that sample to be strictly earlier than `lease_expires_at`; it MUST atomically replace and sync the evidence as `armed` with that same sample as `committed_at` and then invoke the target replacement without an intervening external call, blocking wait or lock acquisition. Failure of the initial check, final check or evidence update MUST remove the staged target and any evidence from this attempt, leave prior target bytes unchanged and report `uncommitted`. That final lease-fence sample and its immediately following evidence-and-target critical sequence are the adapter's one commit boundary. After passing it, the adapter MUST atomically replace and sync the target bytes and atomically replace and sync the evidence as `committed`. After process loss, a status query that acquires the lock MUST return `uncommitted` when evidence is absent. Matching `committed` evidence MUST return `committed` and its stored `committed_at`. Matching `prepared` evidence proves the final fence never committed and MUST be atomically removed before returning `uncommitted` without inspecting or changing target bytes. For matching `armed` evidence, the query MUST validate target ownership and mode and compare its SHA-256 with `target_sha256`; an exact match MUST atomically promote the evidence to `committed` and return its stored `committed_at`, while a mismatch MUST atomically remove the evidence and return `uncommitted`. This deliberately treats pre-existing identical target bytes as the authorized logical commit only after armed evidence proves the final lease fence committed. Malformed or identity-mismatched evidence MUST be `store-unavailable` without target or evidence mutation. Evidence MUST remain until the corresponding target binding may be deleted after tombstone retention.

A lease record MUST contain exactly `version` (integer `1`), non-empty `provider`, `account_id` and `consumer_run_id`, lowercase RFC 4122 UUIDv4 `record_id`, and UTC RFC 3339-second `lease_started_at` and `lease_expires_at`. `lease-create` MUST set `lease_started_at` to manager time when that effect commits and `lease_expires_at` to exactly that time plus the normalized request's `lease_seconds`; an identical retry that reclaims its own lease MUST retain both stored timestamps without extending them. Releasing or expiring a lease MUST delete this live-lease record; the assignment or tombstone retains the actual end time.

An assignment record MUST contain exactly `version` (integer `1`), `status` (`prepared` or `committed`), `request`, non-empty `target_ref`, `account_id`, `value_generation` and `value_ref`, lowercase RFC 4122 UUIDv4 `record_id`, `receipt`, UTC RFC 3339-second `lease_started_at` and `lease_expires_at`, nullable UTC RFC 3339-second `target_committed_at` and `actual_lease_ended_at`, `report_markers` and nullable `completion`. A non-null `actual_lease_ended_at` MUST be no earlier than the later of `lease_started_at` and non-null `target_committed_at` and no later than `lease_expires_at`. `value_generation` MUST be a lowercase RFC 4122 UUIDv4 copied from the selected credential. `request` MUST be the exact normalized provisioning request. `receipt` MUST contain exactly lowercase RFC 4122 UUIDv4 `record_id`, non-empty `account_id` and `purpose`, plus UTC RFC 3339-second `validated_at` and `lease_expires_at`; its `validated_at` MUST equal the `last_validated` of the exact authoritative eligible credential reread used to create that prepared assignment. `report_markers` MUST be an array of unique objects containing exactly UTC RFC 3339-second `occurred_at` and a `classification` from the report's closed set, sorted by `occurred_at` and then by the UTF-8 bytes of `classification`. A non-null `completion` MUST have the exact completion-input shape.

An assignment's `target_committed_at` MUST be non-null exactly when `status` is `committed`. A `prepared` assignment MUST have null `target_committed_at`, null `actual_lease_ended_at`, an empty `report_markers` array and null `completion`. Any violation of those status-field relations makes the manager-local record malformed and MUST return `store-unavailable` under the common local-record rule.

A tombstone record MUST contain exactly `version` (integer `1`), the assignment's normalized `request`, non-empty `target_ref`, `account_id`, `value_generation` and `value_ref`, lowercase RFC 4122 UUIDv4 `record_id`, UTC RFC 3339-second `lease_started_at`, `lease_expires_at`, `target_committed_at`, `actual_lease_ended_at` and `closed_at`, plus its `report_markers` and nullable `completion` with the assignment shapes above. Its `actual_lease_ended_at` MUST be no earlier than the later of `lease_started_at` and `target_committed_at` and no later than `lease_expires_at`; `closed_at` MUST equal the operation's stored `accepted_at` for report, complete or release and MUST equal `lease_expires_at` for expire or post-commit prepared-state expiry; it records that command-specific logical closing instant rather than uniformly recording command acceptance. The initial manager MUST retain every tombstone and its target binding indefinitely; deletion requires a later specification revision with its own crash-safe protocol.

A write-ahead operation record MUST contain exactly `version` (integer `1`), `operation_id` (a lowercase RFC 4122 UUIDv4), `command` (`acquire`, internal `reacquire`, internal `revalidate`, `target`, `provision`, `report`, `complete`, `release` or internal `expire`), `phase`, `idempotency_key` (lowercase SHA-256 hex), UTC RFC 3339-second `accepted_at`, `normalized_input`, nullable `terminal_result`, `ordered_effects` and `completed_step`. `phase` MUST be `launch`, `terminal` or `recovery` for acquire, reacquire and revalidate; `issue` for target; `start`, `cleanup` or `postcommit` for provision; `apply` for report, complete and release; and `close` for expire. `normalized_input` MUST be the command's exact validated input with provisioning defaults materialized; acquire adds its generated `record_id` and `next_value_generation`, reacquire contains exactly `record_id` and `next_value_generation`, revalidate contains exactly `record_id`, report contains exactly `version`, `consumer_run_id`, `record_id`, `occurred_at` and `classification` while omitting `diagnostic`, and expire contains exactly `consumer_run_id` and `record_id`. `terminal_result` MUST be null outside a worker `terminal` or `recovery` phase. In an acquire or reacquire `terminal` phase it MUST contain exactly `outcome` (`success` or `failure`), nullable canonical `validated_at`, nullable canonical `published_at`, nullable canonical `expires_at` and nullable `failure_reason`; success MUST have the first two timestamps non-null, null `failure_reason`, `published_at` no earlier than `validated_at` and `expires_at` either null or later than `published_at`, while failure MUST have all three timestamps null and `failure_reason` equal to `provider-rejected`, `flow-unavailable` or `step-limit`. In a revalidate `terminal` phase it MUST contain exactly `outcome`, nullable canonical `validated_at` and nullable `failure_kind`; success MUST have non-null `validated_at` and null `failure_kind`, while failure MUST have null `validated_at` and `failure_kind` equal to `rejected` for definitive credential rejection or `inconclusive` for every other failure. A worker `recovery` phase MUST carry that command's exact failure terminal-result shape. Acquisition and reacquisition recovery MUST use `failure_reason` `flow-unavailable`; fenced revalidation recovery MUST use `failure_kind` `inconclusive`, making the durable target state `suspect`; `rejected` makes it `dead`. A terminal result contains no raw value; on live acquisition success the browser-control service retains the capture only in its private descriptor until its direct descriptor transfer to `secret-value-set`. Recovery MUST inspect the exact desired complete metadata postcondition before replacing a no-longer-live worker's terminal success: when that record is already authoritative it MUST retain success and advance the unmarked `credential-conditional-set`; otherwise it MUST enter the distinct recovery phase below even when acquisition already created an unreferenced value item.

`ordered_effects` MUST be a non-empty array whose entries come only from `worker-record-create`, `audit-append`, `secret-value-set`, `credential-conditional-set`, `worker-record-remove`, `registration-remove`, `issuance-create`, `lease-create`, `prepared-assignment-create`, `target-write`, `assignment-commit`, `prepared-assignment-discard`, `selection-update`, `proof-update`, `report-marker-update`, `completion-update`, `assignment-end-update`, `lease-release`, `tombstone-create` and `assignment-close`. Repeated effect names are permitted and `completed_step` is their positional index from `-1` through the last array index. Effects MUST appear in required contract order. After every effect in one phase commits and the contract-defined transition condition is known, the manager MUST atomically replace the record with its contract-defined next phase and that phase's complete effect array while resetting `completed_step` to `-1`; it MUST NOT otherwise rewrite the plan or remove a record whose current phase is nonfinal. The rewrite exception is either a fenced or no-longer-live worker whose terminal success neither has its `credential-conditional-set` marked complete nor has that effect's exact desired metadata postcondition authoritative, or a live acquisition or reacquisition worker whose terminal-success `secret-value-set` returned `uncommitted`, unavailable or malformed output, reached its deadline or was interrupted. Only after the applicable postcondition or result check, recovery MUST atomically replace the phase with `recovery`, replace `terminal_result` with the command's failure form, install the complete recovery effect array and reset `completed_step` to `-1`; for revalidate it MUST use `failure_kind` `inconclusive`. Because the phase changes, every recovery effect has an identifier distinct from every prior terminal attempt and uses `recovery-writer`. An authoritative exact desired metadata record MUST instead preserve terminal success and advance that unmarked effect. Any unfinished acquisition `secret-value-set` whose later metadata postcondition is not authoritative MUST be abandoned by that phase replacement; its possibly created item remains unreferenced. Provision `start` MUST transition to `postcommit` after a committed target and to `cleanup` after a pre-commit failure with committed start effects. A completed acquire, reacquire or revalidate `launch` MUST remain durable until its worker persists a terminal outcome or recovery chooses failure: the former MUST transition to `terminal` with that complete terminal result, while the latter MUST transition directly to `recovery` with the command's failure form and complete recovery effect array. A worker operation MUST NOT enter terminal success after its worker was fenced. Every retry MUST reuse `accepted_at`, which MUST be the manager's current time immediately after pre-operation validation. For report, completion or release, `normalized_close_time` MUST equal the latest of stored `lease_started_at`, stored non-null `target_committed_at` and the earlier of stored `accepted_at` and `lease_expires_at`; `assignment-end-update` MUST use that value as `actual_lease_ended_at`, while `closed_at` MUST use stored `accepted_at` and MAY precede `normalized_close_time` only after a backward wall-clock step. `assignment-commit` MUST record the adapter-supplied target commit time and change `status` to `committed`; `prepared-assignment-discard` MUST remove an uncommitted assignment.

Each ordered-effect position MUST have the logical `effect_id` equal to lowercase SHA-256 of `LP(operation_id) || LP(command) || LP(idempotency_key) || LP(phase) || LP(base10-index)`, where `base10-index` is the position's non-negative ASCII decimal spelling without a leading zero except `0`. The identifier is derived rather than added to the closed operation record. After taking the effect's required locks, every executor MUST inspect authoritative state for that position's exact postcondition before performing it, except that `secret-value-set` MUST perform no values-vault postcondition read and follows its write-once rule below. An already satisfied postcondition MUST advance `completed_step` without repeating the effect; its exact predecessor permits the effect to run; and any other state MUST follow an explicitly defined conditional no-op or refusal, otherwise return `store-unavailable` without overwriting it. Create effects MUST derive complete content from the operation and the authoritative sources fixed here. `worker-record-create` MAY create only the record for a newly spawned held child still owned by the current launcher; it MUST set `started_at` to manager time immediately after capturing that child's `worker_pid` and `worker_start_ticks`, derive `deadline` from that time, and treat the one valid live record matching the operation's `record_id` and worker kind as committed. An absent or nonlive record after launcher loss follows the launch-abandonment rule and MUST NOT spawn a replay worker; a different or duplicate record is `store-unavailable`. `issuance-create` MUST first scan validated issuance records for the operation's `consumer_run_id` and adapter: exactly one matching unexpired record is its committed success postcondition and supplies the original reference; exactly one expired unbound record is its committed non-reissuable refusal postcondition; none permits one adapter issuance and record creation; and a conflict or duplicate is `store-unavailable`. Recovery of an expired record MUST finish any pending registration removal and operation housekeeping before returning `invalid-request`, without an adapter call or replacement issuance. `lease-create` MUST scan validated leases for its operation's `consumer_run_id` at one captured manager time: exactly one live lease matching that run and the request provider is committed and supplies its original account, record and lease times; any matching expired lease is absent for this postcondition and neither satisfies it nor conflicts with a live result; a duplicate or conflicting live lease is `store-unavailable`; and no matching live lease permits fresh deterministic selection followed by atomic creation from the operation's normalized request, that selected credential and manager time, replacing an expired lease at the selected account path only after proving it remains expired. `prepared-assignment-create` MUST inspect the run's assignment path: one exact prepared assignment is committed; a conflicting assignment is `store-unavailable`; and absence permits creation only from the operation's normalized request, its matching issuance, the one matching live lease and an authoritative eligible reread of the leased credential, which together supply every assignment and receipt field. Delete effects MUST treat absence after their required predecessor effect as the committed postcondition. Audit append MUST use `effect_id` as defined above, `credential-conditional-set` MUST use authoritative reconciliation, and target write MUST use target-commit evidence. These checks MUST make an effect commit followed by a crash before `completed_step` advancement replay as one logical effect.

The stored idempotency key MUST be lowercase SHA-256 of: `LP(provider) || LP(account_id) || LP(kind) || LP(purpose)` for `acquire`; `LP(record_id)` for `reacquire` and `revalidate`; `LP(consumer_run_id)` for `target` and `provision`; `LP(consumer_run_id) || LP(record_id) || LP(occurred_at) || LP(classification)` for `report`; `LP(consumer_run_id) || LP(record_id)` for `complete`, `release` and `expire`. A direct acquire identity, provision run, completion identity and expiration identity therefore resolves its command's operation path before normalized-input equality is checked; an acquire retry locates a reacquire path through the exact metadata identity lookup defined above.

Each audit line MUST contain exactly `version` (integer `1`), lowercase RFC 4122 UUIDv4 `record_id`, lowercase SHA-256 `effect_id`, `actor`, `operation`, and UTC RFC 3339-second `attempted_at`. `effect_id` MUST be the logical ordered-effect identifier defined above, or for the operation-less lifecycle-expiry exception the lowercase SHA-256 of `LP("expire-lifecycle") || LP(record_id) || LP(current_value_generation) || LP(expires_at)`, where `current_value_generation` is the record's UUID string when non-null and the empty string otherwise. For that exception, this one digest MUST be both the audit line's deduplication identity and the `credential-conditional-set` effect identifier used in its append-only revision title and pending fence; fence relation validation MUST recompute that same digest from the authoritative expiring record. `attempted_at` MUST be manager time captured for the first adapter attempt represented by that audit line and is informational rather than part of the replay match above. `actor` MUST be exactly `acquisition-writer`, `lifecycle-writer`, `report-writer` or `recovery-writer`; `operation` MUST be exactly the attempted effect name `secret-value-set` or `credential-conditional-set`. Actor names identify the semantic owner below even when another process resumes its operation:

| Audited effect | Actor |
|---|---|
| Acquire launch's initial credential create; acquire or reacquire terminal `secret-value-set`; acquire or reacquire terminal-success complete-record publish | `acquisition-writer` |
| Reacquire launch; a live acquisition or reacquisition worker's terminal-failure transition; revalidate launch; a live revalidation worker's success, rejected or inconclusive terminal transition | `lifecycle-writer` |
| Report's generation-conditioned credential transition | `report-writer` |
| Lifecycle expiry and every `recovery`-phase credential conditional-set for a fenced or lost worker or a live worker abandoning an unacknowledged `secret-value-set` | `recovery-writer` |

Except for a missing record with its defined meaning, any malformed, non-regular, symlinked, incorrectly owned or more-broadly-accessible manager-local file MUST return `store-unavailable` with exit `4` without reset or mutation. A malformed attention artifact counts as unreadable attention state. Run registrations retain their narrower typed refusal contract above; worker records retain their fail-closed liveness contract above.

Before a command applies effects across the provisionable-token store and manager-local state, it MUST persist a secret-free write-ahead operation record containing its operation id, idempotency key, phase, ordered effects and completed-step marker. A new operation record MUST generate a fresh `operation_id`; every retry, recovery and phase replacement of that record MUST retain it byte-for-byte, and any later operation created after that record's terminal removal MUST generate a different one. The single-audited-conditional-mutation lifecycle-expiry exception creates no operation record because its only manager-local effect is the append-only attempt evidence and its only substantive mutation is one SecretStore compare-and-set. Configuration, invocation and exact input-shape validation MUST finish before any recovery or mutation. A request refused by later run-reuse, pending-operation, prepared-assignment, tombstone, assignment-ownership or target-reference validation MUST leave no new command operation or other mutation, except for explicit pending-operation resumption, assignment-expiration recovery, `target` registration-expiration recovery, or the mandatory global recovery effects of metadata-fence reconciliation, worker fencing or reconciliation, credential expiry and stale-attention removal in the sequence above.

Every manager lock MUST be a Linux `flock` held on an open owner-only regular non-symlink lock file: per-run at `<manager-state>/locks/run/<sha256(LP(consumer_run_id))>.lock`, destination at `<manager-state>/locks/destination/<sha256(LP(canonical_destination_identity))>.lock`, provider-account at `<manager-state>/locks/provider-account/<sha256(LP(provider) || LP(account_id))>.lock`, lease-record at `<manager-state>/locks/lease/<sha256(LP(provider) || LP(account_id))>.lock`, credential-record at `<manager-state>/locks/credential/<sha256(LP(record_id))>.lock`, attention-artifact at `<manager-state>/locks/attention/<sha256(LP(record_id))>.lock`, target-reference at `<manager-state>/locks/target/<sha256(LP(target_ref))>.lock`, audit-log at `<manager-state>/locks/audit.lock`, selection-state at `<manager-state>/locks/selection-state.lock`, and proof-record at `<manager-state>/locks/coexistence-proof.lock`. Each file MUST be mode `0600` beneath owner-only mode-`0700` directories and contain no authoritative state. A target command MUST hold its destination lock from before cross-run destination discovery through authoritative `issuance-create` commit and release it before registration removal. A held acquisition or reacquisition worker MUST remain the owner of its provider-account serialization after launcher release. A revalidation worker MUST inherit no manager lock and hold none during its provider probe, then for terminal persistence MUST acquire credential-record serialization and its nested audit-log lock in the declared order within their bounded waits. A final provisioning write or status call MUST own its target-reference serialization until its terminal outcome or exit. The kernel MUST release every lock when its last owning process ends, even if the lock file remains. A contender MAY classify a contended provider-account lock as the matching active worker's lock only when the same account has exactly one matching authorized live worker record whose lifecycle state is active; otherwise it is other contention. Every `lease-create` MUST take its lease-record lock with `LOCK_NB`; an account whose try contends MUST be excluded from normal selection, recovery-candidate revalidation and dead-record replacement for the rest of that provision invocation. Selection MUST make at most one such try per otherwise eligible account. If, after normal selection, recovery-candidate handling and any required replacement launch, no eligible unexcluded candidate remains, the manager MUST remove its still-empty pre-lease provision operation and return `retryable-exhaustion` with exit `3`, leaving the target byte-identical and `consumer_run_id` unconsumed; a required dead-record replacement launch MUST occur before that removal and return. Every `lease-release` and expiration cleanup MUST hold the same lock through its conditional file transaction. A commit-status query MUST try its target-reference lock with `LOCK_NB` and return `in-progress` on contention. Every lock acquisition declared non-blocking MUST use `LOCK_NB`. Every other lock wait, including destination-lock acquisition, MUST stop within `external_call_timeout_seconds` and return `store-unavailable` without substantive mutation if not acquired.

Target, provision, report, complete, release and expire MUST serialize manager-local effects per `consumer_run_id`. A pending run-scoped operation means exactly one nonterminal `target`, `provision`, `report`, `complete`, `release` or `expire` write-ahead record for that run. After syntactic validation and under the run lock, each command MUST enumerate that closed set. More than one is `store-unavailable`; a conforming manager MUST NOT create a second while one remains. Any command MUST resume a pending target `issue`, provision `cleanup` or `postcommit`, or report, complete, release or expire operation from its stored input before evaluating the requested operation. A pending provision `start` may instead be resumed only by an identical provision request and only after global mandatory recovery; every other requested command MUST return its command-specific invalid input result after that global recovery, cause no further mutation and MUST NOT create expiration state. Thus provision `postcommit` always finishes and its operation is removed before an expired committed assignment can create or resume `expire`; provision and expire records cannot conformingly coexist. An identical requested command MUST also resume its own eligible phase at the position just defined. The resumed operation's stored `accepted_at` fixes any tombstone times, after which the requested command re-evaluates the resulting assignment or tombstone and only then performs required assignment-expiration recovery. Report MUST then take the credential's per-record serialization, hold it through the paired audit and `credential-conditional-set` plus any cache eviction, and release it before `proof-update` or any later `lease-release`. Acquire and reacquire MUST take the provider-account lock before the credential-record lock. All commands MUST take simultaneously held locks only in the order per-run, destination, provider-account, lease-record, credential-record, attention-artifact, target-reference, audit-log, selection-state, proof-record, omitting inapplicable locks. A target-reference lock MUST remain held throughout its adapter write or commit-status query. A recovery that must move from credential-record to provider-account serialization MUST release the record lock first and re-take it after acquiring or reusing the account lock; any second lock of the same rank MUST be tried non-blockingly. Every read-modify-write of `selection-state.json` and `coexistence-proof.json` MUST hold its named exclusive lock through atomic replacement, preventing lost updates across runs.

Applicable effects MUST appear in this relative order. Acquire and reacquire `launch` MUST contain exactly `worker-record-create`, `audit-append`, `credential-conditional-set`; their `terminal` phase MUST contain exactly `audit-append`, `secret-value-set`, `audit-append`, `credential-conditional-set`, `worker-record-remove`. The first audit MUST use operation `secret-value-set` and the second MUST use `credential-conditional-set`. Acquire, reacquire and revalidate `recovery` MUST contain exactly `audit-append`, `credential-conditional-set`, `worker-record-remove`, using operation `credential-conditional-set` and actor `recovery-writer`; this phase records the command's failure lifecycle transition and never attempts a value write. On acquired success, `secret-value-set` MUST attempt creation of the operation's generation exactly once, without a values-vault postcondition read, and MUST mark the effect complete only after a positive creation acknowledgement. An explicit `uncommitted`, unavailable or malformed result, deadline or interruption MUST NOT retry that generation: the live worker, or recovery after a crash with that effect unfinished, MUST enter the recovery phase defined above. Any unacknowledged created item remains unreferenced; every later acquire or reacquire MUST use its newly generated `next_value_generation`. After a positive acknowledgement, the metadata conditional-set publishes the generation as `valid` with the terminal result's `validated_at`; on a live terminal failure, `secret-value-set` is a completed no-op and the metadata conditional-set records the terminal lifecycle state. Revalidate `launch` MUST use the same exact launch array and its `terminal` phase MUST contain exactly `audit-append`, `credential-conditional-set`, `worker-record-remove`; its worker MUST make exactly one provider probe, terminal success sets `status` to `valid` and `last_validated` to its stored `validated_at`, `rejected` failure sets status to `dead`, and the first inconclusive result MUST be terminal and transition `revalidating` to `suspect` through the audited conditional-set. Target `issue` MUST contain exactly `issuance-create`, `registration-remove`. Provision `start` MUST contain exactly `lease-create`, `prepared-assignment-create`, `target-write`; `postcommit` MUST contain exactly `assignment-commit`, `selection-update`, `proof-update`. That `proof-update` MUST set or retain `rollout_started_at` for every committed `anthropic` assignment whose purpose is `factory`; after that start update it MUST otherwise be a completed no-op unless the assignment is committed `spread`, `simultaneous_spread` is null and an eligible Anthropic factory-purpose peer exists. `cleanup` MUST contain `prepared-assignment-discard` when prepared state exists and MUST always end with `lease-release` whenever any `start` effect committed; that release is a completed no-op when no matching lease remains, so cleanup is never empty. Synchronous revalidation and provision-triggered replacement MUST use their own revalidate or reacquire operation rather than adding worker effects to the provision record. Report `apply` against a live assignment MUST contain exactly `audit-append`, `credential-conditional-set`, `proof-update`, `report-marker-update`, `assignment-end-update`, `lease-release`, `tombstone-create`, `assignment-close`; against a tombstone it MUST contain exactly the first four effects. The credential effect and its paired audit MUST be completed no-ops for `unknown`, a replaced generation, or a matching generation whose credential is already `suspect`, `dead` or `reacquiring`; proof-update MUST be a completed no-op except for an authentication report qualifying under the coexistence-proof rule, so the persisted array never depends on that outcome. `report-marker-update` MUST insert the new unique marker in the assignment or tombstone's declared canonical order. Complete `apply` against a live assignment MUST contain exactly `proof-update`, `completion-update`, `assignment-end-update`, `lease-release`, `tombstone-create`, `assignment-close`; against a tombstone with null completion it MUST contain exactly the first two. Release `apply` against a live assignment and expire `close` MUST contain exactly `assignment-end-update`, `lease-release`, `tombstone-create`, `assignment-close`; release against a tombstone creates no operation and returns its defined no-op. For report, complete or release, `assignment-end-update` MUST conditionally set `actual_lease_ended_at` to the operation's defined `normalized_close_time`; for expire it MUST use `lease_expires_at`. `lease-release` MUST be a completed no-op when no matching live lease remains. Tombstone creation MUST commit before assignment removal; while both files survive that crash window, the tombstone is authoritative and reuse remains refused.

A retry MUST resume the first uncommitted effect from the operation record and MUST NOT answer `duplicate` until every required effect commits. Every multi-step command MUST likewise resume rather than omit a pending effect. Only an existing operation record is nonterminal and counts as pending. Successful completion of every ordered effect MUST then remove it; operation-record removal is terminal housekeeping and is not itself an `ordered_effects` entry. After acquiring that operation's launch serialization, if a `launch` operation has no worker record before `worker-record-create`, or its held worker is no longer live before its initial lifecycle transition committed, recovery MUST remove any worker record and the operation record without changing credential state; a later invocation starts a new launch plan. If active lifecycle state became visible, fenced or interrupted worker recovery MUST instead complete its terminal transition, remove the worker record and remove the owning acquire, reacquire or revalidate operation record; a later acquire therefore treats a dead credential through the replacement lifecycle rather than resuming validation.

When provision's authoritative reread abandons a selected record after lease acquisition, it MUST atomically enter `cleanup`, discard any prepared assignment, conditionally release that run's lease, remove the completed operation and perform the restart-admission check before creating any replacement operation or retrying selection. That check MUST authoritatively reread the issuance under run serialization and require the target reference to remain matching and unexpired and its registered adapter to remain enabled; an expired or mismatched issuance or disabled adapter MUST return `invalid-request` with exit `2` without a new operation, selection or target write, while success permits a new provision operation with newly captured `accepted_at`. The same restart rule MUST apply when `lease-create` is complete but `prepared-assignment-create` finds no matching live lease because it expired or was conditionally replaced before the assignment existed: that operation MUST enter `cleanup` with only its required conditional no-op `lease-release`, remove the completed operation, apply that same restart-admission check, and only on success create the fresh operation and retry selection; it MUST NOT remain stuck or create from another run's lease. A pre-commit domain failure after any provision `start` effect committed uses the same cleanup path but returns after removing the operation, so the run is then reusable for a corrected request; failed cleanup retains nonterminal state and returns `store-unavailable`. A pre-commit domain failure before any `start` effect committed MUST remove the provision operation directly without entering an empty cleanup phase. A target-committed prepared assignment whose lease expired MUST first finish the provision `postcommit` phase from the adapter's `committed_at`, remove the provision operation and then run the explicit expire operation through tombstone creation and assignment removal. A failed required audit append, provisionable-token store mutation or manager-local transaction MUST return `store-unavailable` with exit `4` and MUST NOT acknowledge report, complete or release. Effects already marked complete remain committed; later effects remain pending and safety-critical exclusion remains in force. Before a provisioning target commits, such a failure MUST leave target bytes unchanged. A failure after target commit is instead the post-commit `internal-bug` recovery case below.

### Provisioning request and target

A target request MUST contain only `version` (the integer `1`), non-empty `consumer_run_id` and non-empty `adapter`. Requiring that adapter to be registered and present in `enabled_target_adapters` is a command-specific predicate in the exact pre-recovery validation order, after configuration and object-shape validation but before recovery; an unregistered or registered-but-disabled adapter MUST return `invalid-request` without recovery, adapter invocation or mutation. The manager MUST invoke the enabled `ProvisioningTarget` adapter to issue an opaque, unguessable reference bound to the run, persist the issuance record and return the reference plus its UTC RFC 3339-second `expires_at`. An unassigned reference MUST expire 24 hours after issue. A provisioning request MUST contain only `version` (the integer `1`), non-empty strings `provider`, `kind`, `purpose`, `consumer_run_id` and `target_ref`, optional `strategy` (`consume-first` or `spread`, default `consume-first`) and optional integer `lease_seconds` (default `21600`, minimum `60`, maximum `86400`). The lease_seconds integer range is part of exact provisioning-object validation; a value outside it MUST return `invalid-request` before mandatory recovery, target validation, selection or lease acquisition. The normalized provisioning request is that exact object after materializing both optional defaults; when applied to provisioning requests, `identical`, `same logical request` and `exact request` mean field-for-field equality of normalized provisioning requests.

Consumers MUST choose globally unique `consumer_run_id` values and MUST NOT intentionally reuse one. Only a target-committed assignment consumes that identity. Any failure before the target adapter commits leaves the identity reusable for an identical replay while a matching provision operation or prepared assignment remains; after successful prepared-state cleanup removes both, an identical or corrected request may reuse it only while its issuance remains unexpired. An expired issuance becomes the permanent non-reissuable identity record only when it is unbound under the four-state definition above. Repeating the same logical request while its committed assignment lease is live MUST be idempotent and return the original secret-free receipt. A different request that reuses the identity of a live committed assignment MUST return `invalid-request` before target validation, selection or lease acquisition and MUST leave its assignment, receipt and lease unchanged. A non-identical request that meets a pending provisioning operation or prepared assignment for the same identity MUST return `invalid-request` at that same boundary and MUST leave the pending state unchanged; lease expiry alone does not let a corrected request discard it, so the identical request must complete cleanup first. After completion, release, failure report or lease expiry closes a committed assignment, the initial manager MUST retain its assignment tombstone and target binding indefinitely and MUST reject reuse before target validation, selection or lease acquisition. An uncommitted prepared assignment MUST NOT create a tombstone. No manager command performs retention cleanup, and a target adapter MUST never intentionally reissue a reference.

`target_ref` MUST be an opaque reference issued through the manager's target command, not an arbitrary path supplied to the manager. The manager MUST resolve it from the persisted issuance record rather than parse it for a destination. A provision request MUST recognize an identical pending operation, prepared assignment, committed assignment or retained tombstone before applying the issuance expiry; that binding keeps the reference resolvable for recovery and idempotent replay even after its issuance `expires_at`. A fresh provision with no matching pending operation, prepared assignment, committed assignment or retained tombstone MUST require the issuance record's adapter to remain enabled and MUST return `invalid-request` before selection when it is disabled. Recovery or idempotent replay of matching pending, prepared, committed or retained state MUST instead keep using the adapter recorded by the issuance even if configuration later disables it; if that registered implementation is no longer available, the command MUST return `store-unavailable` while retaining the recovery state and MUST NOT discard, reissue or reinterpret the reference. A conforming adapter MUST bind each reference immutably to exactly one consumer-run identity, MUST NOT reassign it, and MUST establish that its resolved destination is writable only within that run's isolated execution target and is neither the host's live interactive-agent credential nor a destination issued to any other run. It MUST validate the binding without receiving credential bytes, serialize writes for the reference, make a successful write atomic and durable, and leave an existing destination byte-identical whenever it returns failure, including after process interruption. For the built-in `isolated-run` adapter, `consumer_run_id` is a logical identity, not an operating-system principal: after success the destination MUST be owned by the manager's effective operating-system user, have mode no broader than `0600`, and sit beneath registered parent directories no broader than `0700`. An absent, expired and unbound, invalid, mismatched, host-wide or shared target reference MUST return `invalid-request` before the manager selects a credential or acquires an account lease.

### Run-scoped leases and provisioning

A lease is live only while its lease record exists and the current time is strictly earlier than `lease_expires_at`; it is expired at or after that instant. Selection MUST acquire a non-blocking per-account lease bound to `consumer_run_id` before the authoritative read and hold it after successful provisioning until the earliest of a matching failure report, completion, explicit release or that expiry. `lease-create` MUST atomically create an absent lease or replace one only after proving the stored lease is expired. Every `lease-release`, including cleanup and expiry, MUST condition deletion on the file still naming the closing `consumer_run_id` and `record_id`; a later run's lease MUST remain untouched. The manager MUST treat an expired lease as absent before selecting, so its account becomes eligible without a crashed consumer's cooperation.

After syntactic validation and under per-run serialization, a command that finds an expired committed assignment MUST create or resume its `expire` operation before assignment ownership or reuse validation. That operation MUST set the assignment's `actual_lease_ended_at` to `lease_expires_at`, conditionally delete only its matching stale lease, create the tombstone with `closed_at` equal to `lease_expires_at`, remove the assignment and then remove the expire record. Required resumption of a pending run-scoped operation and this expiration recovery are the only mutation exceptions for a requested command later refused by the resulting tombstone. Provisioning failure MUST release its lease immediately when cleanup persistence is available. A live lease MUST make that account ineligible to every other request, and contention MUST retry selection rather than block or share an assignment. Release MUST be idempotent. Immediately before invoking the target adapter, the manager MUST bypass every cache and re-read the complete authoritative record, including `value_ref`, status, `last_validated` and expiry, while holding the lease. A changed or ineligible record MUST be abandoned through the provision cleanup-and-restart path above; the adapter MUST receive only the still-current value resolved from that authoritative `value_ref`.

The authoritative pre-provisioning metadata re-read MUST hold the credential-record lock across the uncached complete-chain read and the checks for both a pending metadata-effect fence and any nonterminal acquire, reacquire or revalidate operation. Either presence MUST abandon that candidate through cleanup-and-restart before any value read or target action; the manager MUST NOT provision an intermediate `valid` revision made visible by fence reconciliation.

Before lease acquisition, provisioning MUST persist a write-ahead operation record bound to the run and exact request; an identical retry MUST use it to reclaim only a live lease held by that run without changing its stored lease timestamps and resume the first unfinished step; a same-run lease expired at the `lease-create` postcondition's captured time is absent and MUST NOT be reclaimed. Before invoking the target adapter, the manager MUST atomically persist a prepared assignment containing the run identity, request fields, target reference, selected record identity and `value_ref`, complete secret-free receipt and lease. A prepared assignment MUST reserve that lease and logical request but MUST NOT count as successful provisioning or consume the run identity unless the target commits.

The adapter MUST expose commit status as `in-progress`, `committed` or `uncommitted` plus nullable UTC RFC 3339-second `committed_at`, queried under the same per-reference lock that serializes its write. `committed_at` MUST be non-null exactly for `committed` and MUST equal the adapter's final lease-fence sample at the commit boundary defined by the target-commit evidence transaction above. The built-in adapter MUST derive that status and time only from that transaction. Failure to take that lock, including while a timed-out or parent-orphaned target child still owns it, means `in-progress`, never `uncommitted`; the adapter MUST perform the final lease-fence check immediately before atomic replacement and MUST abort without changing prior target bytes when its sample is at or after `lease_expires_at`. A target write that definitively fails before commit and reports `uncommitted` before its deadline MUST enter provision cleanup and, after successful prepared-assignment discard and lease release, return `provisioning-failed` with exit `5` without selecting or writing again in that invocation. Only a retry of the identical provisioning request MAY act on prepared state left by an ambiguous interruption or deadline: `in-progress` MUST return `retryable-exhaustion` without changing it; `uncommitted` MUST enter provision `cleanup`, discard the prepared assignment, conditionally release the lease, remove the completed operation, apply the restart-admission check and only on success start a new provision operation with newly captured `accepted_at` before resuming selection, without returning the stored receipt or creating a tombstone; and `committed` MUST resume the post-commit path and persist `assignment-commit` from `committed_at`. Report, complete and release MUST treat prepared-only state as invalid input without discarding it, and other selection reads MUST observe its lease as held only while the current time is earlier than `lease_expires_at`. If uncommitted cleanup fails, the retry MUST return `store-unavailable`, retain its nonterminal cleanup state for an identical retry and MUST NOT start the replacement operation or return the domain failure.

For a committed target, the manager MUST idempotently apply every pending post-commit effect. When the assignment lease remains live, it MUST then return the receipt. When the lease expired before this acknowledgement, prepared-state recovery MUST run before the tombstone reuse check, apply the pending effects, set the assignment's `actual_lease_ended_at` to `lease_expires_at`, create the tombstone with `closed_at` equal to `lease_expires_at` and only then remove the assignment, and return `invalid-request` without a success receipt; its redacted message MUST say that the target committed but the lease expired and the credential MUST NOT be used. Every non-identical request evaluates the tombstone normally. During `proof-update` for a committed `spread` assignment whose provider is `anthropic` and purpose is `factory`, while proof `simultaneous_spread` is null, eligible peers MUST be committed `spread` assignments or retained tombstones with that same provider, kind and purpose, a target commit at or after non-null `rollout_started_at`, and a different consumer run and account whose retained actual lease interval overlaps this assignment's interval at the later of their two `target_committed_at` values. An interval contains that instant exactly when `lease_started_at` is no later than it and the instant is strictly earlier than `actual_lease_ended_at` when non-null, otherwise strictly earlier than `lease_expires_at`. The manager MUST choose the peer with the earliest `target_committed_at`, breaking a tie by lexical `consumer_run_id`; order the two members by that same tuple as `first` then `second`; set `overlap_started_at` to their later `lease_started_at`; and set `overlap_ended_at` to their later `target_committed_at`. Prepared-only peers do not qualify. Assignment records and their retained tombstones MUST retain lease start, target commit and actual lease-end times so every retry can derive the same pair.

Success MUST cause the adapter to atomically write exactly the raw credential bytes resolved from the selected `value_ref` to the isolated target, with no added encoding, framing or trailing newline; that target commit plus the durable prepared record makes the assignment successful and consumes the run identity even if the following `assignment-commit` persistence fails. The manager MUST persist that effect and every later post-commit effect before returning the stored receipt containing `record_id`, `account_id`, authoritative `validated_at`, `purpose` and `lease_expires_at`, but no secret bytes. A pre-commit domain provisioning failure whose prepared-state cleanup succeeds MUST return exactly one typed `retryable-exhaustion`, `invalid-request`, `store-unavailable` or `provisioning-failed` result, release any acquired lease, leave the target byte-identical and leave `consumer_run_id` unconsumed. A cleanup persistence failure MUST instead return `store-unavailable` and leave the lease to a later retry or expiry. On an unexpected internal bug before target write begins, the manager MUST enter provision `cleanup`, discard any preparation, release any matching lease and then return `internal-bug`; a cleanup persistence failure MUST instead return `store-unavailable`. If target write may have begun, the manager MUST first query commit status under the target-reference lock. `uncommitted` MUST run that cleanup before `internal-bug`; `committed` MUST follow the post-commit rule; and `in-progress` or an unavailable status result MUST return `internal-bug` while preserving the prepared assignment and matching lease for an identical retry to query again. The manager MUST NOT leave a prepared assignment after releasing its lease. An unexpected internal bug after target commit MUST return `internal-bug` with exit `70` while preserving the run's prepared assignment, receipt and lease, so an identical retry completes pending effects and returns that receipt without another write or selection.

### Failure reports

A consumer report MUST contain only `version` (the integer `1`), non-empty strings `consumer_run_id` and `record_id`, UTC RFC 3339-second `occurred_at`, `classification` from the closed set `authentication`, `rate-limit`, `provider-outage` and `unknown`, and optional redacted string `diagnostic`. After the complete mandatory pre-operation recovery sequence, including required pending run-lifecycle resumption and assignment-expiration recovery, it MUST match either the resulting committed assignment or retained tombstone for that exact run and record; an unknown, prepared-only or mismatched identity MUST return `invalid-report`. After pending-operation recovery and that identity match, a resulting assignment or tombstone whose `report_markers` already contains that `occurred_at` and `classification` MUST cause report to create no operation, apply no effect and return `duplicate` true before interval validation. Otherwise, `occurred_at` MUST be no earlier than the resulting assignment or tombstone's `target_committed_at`, no later than the manager's current time and no later than `lease_expires_at` for an assignment or `actual_lease_ended_at` for a tombstone; a value outside that interval MUST return `invalid-report` without further mutation. Reporting the same run, record, time and classification more than once MUST be idempotent after every write-ahead effect completes; a newly completed report MUST return `duplicate` false. A present `diagnostic` is mechanically redacted exactly when its UTF-8 encoding is at most 1024 bytes, contains no ASCII control character and matches no registered provider-kind token matcher. A diagnostic failing that rule MUST return `invalid-report` before recovery, operation creation or mutation. A valid diagnostic MUST be discarded before operation persistence; it is excluded from normalized-input equality, so a repeat that differs only by absent or different diagnostic text is the same report and follows the same pending-resume or duplicate result.

Authentication, rate-limit and provider-outage MUST release any live reporting-run lease before acknowledgement. After mandatory recovery and authoritative report-record validation but before creating a report operation, a report against a current `acquiring` credential MUST return `invalid-report` because that record could not have been provisioned; this refusal precedes and is excluded from the value-generation mismatch rule below. For every other current state, the lifecycle transition MUST be a compare-and-set conditioned on the matching assignment or tombstone's stored `value_generation` still equaling the record's current `value_generation`, including when resumed from a write-ahead record. When that comparison succeeds, it MUST transition a current `valid` or `revalidating` record to `suspect`. An already `suspect`, `dead` or `reacquiring` record MUST make both `audit-append` and `credential-conditional-set` completed no-ops with no adapter call or cache eviction. When the value generations differ on a non-`acquiring` record, that effect MUST likewise become a completed no-op: the manager MUST accept the report and release any live lease but MUST NOT change or invalidate the replacement credential's lifecycle or cache entry. Authentication MUST still apply its event-time proof effect before acknowledgement. `unknown` MUST leave lifecycle status unchanged and release any live lease. When reporting a live assignment, the manager MUST set the assignment's `actual_lease_ended_at` to the operation's `normalized_close_time`, create the tombstone with `closed_at` equal to accepted time and then remove the assignment. A first report against an existing tombstone whose marker is not stored MUST apply its `audit-append`, conditional `credential-conditional-set`, `proof-update` and `report-marker-update` effects and MUST omit `lease-release`, `tombstone-create` and `assignment-close`; no-op rules still mark its first two positions complete without an append or adapter call when applicable, and the stored-marker duplicate rule prevents every one of those effects from running again. A report of any classification MUST NOT synthesize or modify the provider health adapter remainder consumed by `health_strategy`; a later selection obtains that observation independently. A `suspect` record MUST return to `valid` only through the successful revalidation transition defined in spec.md. Apart from every run-scoped or global mandatory recovery effect the command was required to finish before evaluating the new report, an `invalid-report` outcome MUST preserve all credential, proof and lease state; the refused report itself MUST cause no further mutation. A report MUST NOT expose credential material.

### Backend cache

Metadata reads from every provisionable-token store backend MUST use an in-process memory cache whose maximum entry age is the configured `backend_cache_interval_seconds` defined under Configuration and state; the cache MUST NOT outlive its command or detached worker process. Metadata entries MUST key by `record_id` and the current logical revision's `item_id`, not by `value_generation`. Before any cache hit used for lifecycle or selection eligibility, the reader MUST obtain the record's current revision title through an uncached metadata-list operation and MAY use the cached record only when its `item_id` equals that title; a same-generation status revision therefore cannot hit an older `valid` entry in another process. Raw-value reads by the provider observer and final provisioning roles MUST bypass that cache, hold bytes only for their one role call, destroy them when the call ends and never persist them to disk. A metadata write or failed validation MUST evict matching entries in the writing process before acknowledgement. A consumer authentication report MUST evict only when it actually transitions the current `valid` or `revalidating` credential to `suspect`; a replaced-generation or already-`suspect`, `dead` or `reacquiring` no-op MUST preserve the current metadata cache entry. The authoritative pre-provisioning metadata re-read MUST bypass this cache and MUST replace the process-cache metadata entry with the authoritative record or evict it before cleanup-and-restart, including when the generation is unchanged. A cache failure MUST degrade to a store read and MUST NOT make an unvalidated credential eligible.

### Browser-verification attention

A CAPTCHA or two-factor wall MUST create one atomic JSON artifact at `<manager-state>/attention/<sha256>.json`, where `<sha256>` is the lowercase SHA-256 hex digest of the UTF-8 credential `record_id`. It MUST be a regular, non-symlink mode-`0600` file beneath the mode-`0700` manager state directory and contain exactly `version` (integer `1`), `type` (`browser-verification-wall`), lowercase RFC 4122 UUIDv4 `record_id`, lowercase RFC 4122 UUIDv4 `operation_id`, positive integer `worker_pid`, non-negative integer `worker_start_ticks`, non-empty string `provider`, non-empty string `account_id`, `reason` (`captcha` or `two-factor`), `status` (`pending`, `resolved` or `give-up`), UTC RFC 3339-second `raised_at` and `deadline`. Its `provider` and `account_id` MUST equal the owning credential record's immutable fields. It MUST contain no credential, login, mailbox or diagnostic material.

The worker MUST hold the record's attention-artifact lock across artifact creation or removal. Recovery MUST first revalidate and, when required, fence and reconcile the worker while holding only the applicable lower-ranked provider-account and credential locks; it MUST hold no attention-artifact lock during that work. Before taking the attention-artifact lock, recovery MUST release every lower-ranked lock it acquired for that recovery step; a provider-account lock already owned by the enclosing acquire command MAY remain held because taking the higher-ranked attention lock preserves the declared order. Recovery MUST then reread the artifact and worker state and conditionally remove only an artifact still made stale by that completed recovery or its deadline. An operator `--resolve` or `--give-up` action MUST hold it from the pending/authorization/deadline check through its atomic status replacement. Every artifact creation MUST copy `operation_id` from the owning acquisition or reacquisition write-ahead operation and copy `worker_pid` and `worker_start_ticks` from the worker record. After taking the lock each actor MUST re-read the artifact, owning operation and relevant worker record, require the artifact's `operation_id` to equal the operation record's and its two worker fields to equal the worker record's, and require those records still to own the same `record_id`; recovery MUST remove only the old artifact it previously identified, so a replacement worker's artifact survives. A worker MUST release the artifact lock before taking any lower-ranked lock for a give-up lifecycle transition. Thus removal cannot race with an operator update, invert lock order or recreate a removed artifact.

The shared acquisition worker, not a harness binding, MUST own artifact creation and wait only through its deadline, including when provisioning started acquisition asynchronously; an asynchronously started worker MUST survive the provisioning process that launched it. When the artifact deadline is strictly earlier than the worker deadline and passes while the matching artifact remains pending and the worker remains authorized, the worker MUST take the attention-artifact lock, reread and match the artifact, owning operation and worker identities, remove the artifact, destroy every capture, release the attention lock before any lower-ranked lifecycle lock, persist terminal `failed/flow-unavailable` and apply the acquisition or reacquisition lifecycle failure transition to `dead` before releasing its provider-account lock. When the artifact deadline equals the worker deadline, the worker MUST destroy every in-memory capture and exit at that deadline without removing the artifact or persisting a terminal or lifecycle mutation; mandatory global recovery MUST identity-match and remove the artifact, mark the no-longer-authorized worker revoked, confirm its process group ended and enter the owning operation's failure recovery with `failure_reason` `flow-unavailable` before applying the `dead` transition. Every manager command that passes the exact pre-recovery validation order defined later in this operation under Consumer wire protocol MUST recover an artifact whose deadline has passed by the at-or-after definition above or whose acquisition worker is no longer live by applying the state-aware fenced recovery above before reporting attention. `llm-provider-manager attention` with no other argument MUST then discover every pending artifact under the manager state directory and emit exactly one secret-free single-line JSON object `{"version":1,"status":"ok","operation":"attention","items":[...]}`, whose items contain exactly `path`, `record_id`, `provider`, `account_id`, `reason` and `deadline`. Each item MUST copy `provider` and `account_id` unchanged from the validated artifact. Each `path` MUST be the absolute `<manager-state>/attention/<sha256>.json` path, and items MUST sort by the UTF-8 bytes of that absolute path. If attention state cannot be read, it MUST emit the common single-line `store-unavailable` error object and exit `4`.

The same executable MUST expose the mutually exclusive local-operator actions `llm-provider-manager attention --resolve <record_id>` and `llm-provider-manager attention --give-up <record_id>`. The argument MUST be a lowercase RFC 4122 UUIDv4 and any other spelling MUST return `invalid-request` before recovery. After configuration and exact flag validation, an action MUST require the matching artifact to remain `pending`, its worker to remain authorized and current time to be strictly before both deadlines; otherwise it MUST return `invalid-request` without mutation. A valid action MUST atomically set the artifact status and emit exactly `{"version":1,"status":"ok","operation":"attention-update","record_id":"...","attention_status":"resolved|give-up"}`. Agent roles MUST NOT receive manager-CLI or state-write capability for either action. Each harness binding's invocation layer MUST construct and execute only the exact `attention` list argument vector for zero operator arguments or the exact `acquire --acquisition-json -` argument vector for four valid pairs; it MUST NOT accept, construct, forward or execute an `attention --resolve` or `attention --give-up` vector. The worker MUST remove a resolved artifact and resume execution with its retained step count and browser profile. It MUST remove a give-up artifact, destroy any captured secret and persist terminal acquisition `failed/flow-unavailable` with `failure_reason` `flow-unavailable` before applying the lifecycle transition to `dead`. Only the explicit local-operator `--resolve` action may change a pending artifact to `resolved`; browser observation alone MUST NOT resolve it or consume another acquisition step while the worker waits. Thus this manager-owned artifact is separate from the daemon attention surface defined elsewhere in this file, and thin harness bindings carry no attention behavior.

### Consumer wire protocol

This repository's package metadata MUST declare a console entry point named `llm-provider-manager` mapped to the manager executable. Installing that package into an invoking consumer's execution environment and making the declared name resolvable on its `PATH` are consumer-host integration prerequisites governed by that consumer's contract; absence is an integration failure before this protocol. The executable MUST expose `llm-provider-manager target --target-json <path|->`, `llm-provider-manager provision --request-json <path|->`, `llm-provider-manager report --report-json <path|->`, `llm-provider-manager complete --completion-json <path|->`, `llm-provider-manager release --release-json <path|->` and the argument-free governance query `llm-provider-manager proof-status`. `-` MUST mean standard input. Each command carrying a JSON-path flag MUST read exactly one UTF-8 JSON object and reject trailing non-whitespace or unknown fields. A completion object MUST contain only `version` (the integer `1`), non-empty `consumer_run_id`, non-empty `record_id`, UTC RFC 3339-second `completed_at`, `consumer_class` (`test` or `production`), Boolean `provider_authenticated`, Boolean `alternate_credential_used` and Boolean `legacy_pool_absent`. After the complete mandatory pre-operation recovery sequence, including required pending run-lifecycle resumption and assignment-expiration recovery, completion and release MUST match the resulting committed assignment or retained tombstone the manager issued for that exact run and record; an unknown, prepared-only or mismatched identity MUST return `invalid-request` without further change to credential, proof or lease state. After that identity match, an exact stored completion MUST return `duplicate` true before interval validation. Otherwise, `completed_at` MUST be no earlier than the resulting assignment or tombstone's `target_committed_at`, no later than the manager's current time and no later than `lease_expires_at` for an assignment or `actual_lease_ended_at` for a tombstone; a value outside that interval MUST return `invalid-request` without further mutation.

The package-installed console entry point MUST resolve its product package and companion from the installed `overseer` package built from repository-root `overseer/`. The plugin executable `<plugin-root>/bin/llm-provider-manager` MUST instead resolve them only from `<plugin-root>/overseer/`, the shipped plugin mirror of that same package, and MUST NOT import a separately installed `overseer`. The mirror is a runtime carrier rather than a second implementation authority; its contributor-only lockstep enforcement belongs to non-functional-requirements.md §"Constraints".

Before process replacement, the installed console wrapper MAY import only the `overseer` package initializer and its standard-library-only bootstrap module; that bootstrap MUST import no other product module. As its first manager-owned action after those two imports and before reading any environment value or performing substantive work, the bootstrap MUST remove every inherited entry in the complete closed credential-override set by ASCII-uppercased name without reading its value. It MUST then re-execute the invoking Python interpreter with `-I -S`, an absolute path to its packaged companion and the original manager arguments, preserving standard input, output, error and exit status. Every substantive manager path MUST therefore execute with Python environment variables and all site-package discovery disabled. Inability to establish that isolated companion MUST emit the common `internal-bug` result and exit `70` without substantive mutation.

A matching completion MUST be idempotent for the same fields and MUST update the proof record from qualifying evidence. For a live assignment it MUST set the assignment's `actual_lease_ended_at` to the operation's `normalized_close_time`, release the lease, create the tombstone with `closed_at` equal to accepted time and then remove the assignment. For a tombstone whose `completion` is null, it MUST persist the completion and proof effects without a lease effect; exact stored completion has the preceding duplicate-before-interval behavior. Apart from every run-scoped or global mandatory recovery effect the command was required to finish first, conflicting completion fields for the same run and record MUST return `invalid-request` without further change to the proof record or lease; the refused completion itself MUST cause no further mutation. A release object MUST contain only `version` (the integer `1`), non-empty `consumer_run_id` and non-empty `record_id`. Releasing a live committed assignment MUST set the assignment's `actual_lease_ended_at` to the operation's `normalized_close_time`, delete the lease, create the tombstone with `closed_at` equal to accepted time and then remove the assignment. A release that creates or resumes its own `apply` operation and completes it MUST return `released` true even when its replay finds the lease-release effect already committed; only a release that finds the matching tombstone with no pending release operation returns `released` false without mutation. Every invocation MUST write exactly one single-line UTF-8 JSON object to standard output and MAY write only secret-free diagnostics to standard error.

A successful target request MUST emit `{"version":1,"status":"ok","operation":"target","target_ref":"...","expires_at":"..."}`. A successful provision MUST emit `{"version":1,"status":"ok","operation":"provision","receipt":{...}}`, where the receipt has exactly the five fields defined above. A successful report MUST emit `{"version":1,"status":"ok","operation":"report","duplicate":<boolean>}`. A successful completion MUST emit `{"version":1,"status":"ok","operation":"complete","duplicate":<boolean>}`. A successful release MUST emit `{"version":1,"status":"ok","operation":"release","released":<boolean>}` under the new-or-resumed-operation rule above. Successful proof status MUST emit `{"version":1,"status":"ok","operation":"proof-status","seven_day_complete":<boolean>,"simultaneous_spread_complete":<boolean>,"production_success_complete":<boolean>,"legacy_pool_absence_complete":<boolean>,"deprecation_ready":<boolean>}` with `deprecation_ready` true exactly when all four preceding values are true. A failure MUST emit `{"version":1,"status":"error","error_type":"<type>","message":"<redacted>"}` with no additional fields. Exit `0` MUST mean success; exit `2` `invalid-request` or `invalid-report`; exit `3` `retryable-exhaustion`; exit `4` `store-unavailable`; exit `5` `provisioning-failed`; and exit `70` `internal-bug`.

For `report`, `complete` and `release`, lowercase RFC 4122 UUIDv4 spelling of the input `record_id` is part of exact object-shape validation before recovery; a violation MUST return `invalid-report` for report or `invalid-request` for completion or release without recovery or mutation.

Pre-recovery validation MUST run in this exact order: recognize the subcommand; validate that command's flag cardinality; read and validate configuration; read and decode any command input as UTF-8 JSON; validate its exact object shape, version, field types and every numeric range explicitly declared part of object validation; then apply command-specific predicates such as report diagnostic redaction. A missing or unknown subcommand MUST emit the common single-line `invalid-request` object with exit `2` before configuration, recovery or external access. A missing, repeated or unexpected flag for any command except recognized `report` MUST be `invalid-request`; after recognizing `report`, the equivalent flag, input-read, UTF-8, JSON, shape, version, type or diagnostic failure MUST be `invalid-report`. A configuration failure is always `invalid-request`, including for `report`; therefore a recognized report with both bad flag cardinality and bad configuration returns `invalid-report`, while one with valid flags, bad configuration and malformed input returns `invalid-request`. `attention` accepts either no argument or exactly one of `--resolve <record_id>` and `--give-up <record_id>`; any other shape is `invalid-request`. `proof-status` accepts no argument or flag and MUST read the proof record only after mandatory pre-operation recovery; any other invocation shape is `invalid-request`. `acquire`, `attention` and `proof-status` MAY emit only `invalid-request`, `store-unavailable` or `internal-bug`. `target`, `complete` and `release` MAY emit only `invalid-request`, `store-unavailable` or `internal-bug`; `report` MAY emit only `invalid-request` for configuration failure, `invalid-report`, `store-unavailable` or `internal-bug`; and `provision` MAY emit only `invalid-request`, `retryable-exhaustion`, `store-unavailable`, `provisioning-failed` or `internal-bug`. No other exit code or error type MAY be emitted by any manager command.

### Coexistence proof record

The manager MUST keep one owner-only, atomically replaced regular non-symlink JSON record at `<manager-state>/coexistence-proof.json`. It MUST contain exactly `version` (integer `1`), nullable UTC RFC 3339-second `rollout_started_at`, `successful_consumer_dates` (the sorted unique RFC 3339 UTC full-date strings in `YYYY-MM-DD` form in the current consecutive soak), `completion_markers`, nullable UTC RFC 3339-second `soak_started_at`, nullable `simultaneous_spread`, nullable `production_success`, nullable `legacy_pool_absence_success`, and nullable UTC RFC 3339-second `last_auth_failure_at`. `completion_markers` MUST be an array whose entries contain exactly non-empty `consumer_run_id`, lowercase RFC 4122 UUIDv4 `record_id` and UTC RFC 3339-second `completed_at`, are unique by the two identity fields and are sorted by `completed_at`, then lexical `consumer_run_id`, then lexical `record_id`. `simultaneous_spread`, when non-null, MUST contain exactly non-empty `first_consumer_run_id`, `first_account_id`, `second_consumer_run_id` and `second_account_id` plus UTC RFC 3339-second `overlap_started_at` and `overlap_ended_at`. At proof-update creation, the account ids and run ids MUST differ, `overlap_started_at` MUST be copied from the later lease start and may precede `rollout_started_at`, and `overlap_ended_at` MUST be copied from the second assignment's `target_committed_at` and be no earlier than `overlap_started_at`, proving both leases were live at that deterministic instant. Standalone proof-record validation MUST enforce the distinct identities, internal timestamp order and rollout relation from the proof record itself; it MUST NOT require assignments or tombstones that may no longer exist to reconstruct the two copied source instants. `production_success` and `legacy_pool_absence_success`, when non-null, MUST each contain exactly non-empty `consumer_run_id` and UTC RFC 3339-second `completed_at`. When `rollout_started_at` is null, every other nullable field MUST be null and both arrays MUST be empty; when it is non-null, every other non-null timestamp except `simultaneous_spread.overlap_started_at`, every completion-marker timestamp and every successful date MUST be no earlier. The dates MUST be non-empty exactly when `soak_started_at` is non-null; when non-empty, the first date MUST equal the UTC date of `soak_started_at` and each following date MUST be exactly the next UTC date. Record validity MUST NOT depend on the reader's current clock, so a later backward wall-clock step cannot make previously accepted evidence malformed. A record violating those standalone-validity relations is malformed.

For proof-record validity, “no earlier” compares each `successful_consumer_dates` value as a UTC calendar date with the UTC calendar date of `rollout_started_at`; every full timestamp retains instant comparison. A completion on the same UTC date as a later-in-that-day rollout start therefore produces a valid first soak date.

An absent proof file MUST mean the initial object `{"version":1,"rollout_started_at":null,"successful_consumer_dates":[],"completion_markers":[],"soak_started_at":null,"simultaneous_spread":null,"production_success":null,"legacy_pool_absence_success":null,"last_auth_failure_at":null}`. A malformed, incorrectly owned or more-broadly-accessible proof file, or a non-regular or symlinked path, MUST return `store-unavailable` with exit `4` and MUST NOT be reset or mutated. Every post-commit proof update for an `anthropic` assignment whose purpose is `factory` MUST set `rollout_started_at` to its `target_committed_at` when the field is null or that time is earlier, and otherwise retain it; no other provision may change that field. `simultaneous_spread` MUST be set only by the exact committed-assignment proof-update eligibility, instant-containment, peer-choice and pair-ordering rules above when both assignments have provider `anthropic`, purpose `factory` and target-commit times at or after non-null `rollout_started_at`, regardless of whether either consumer is test or production class; the first qualifying pair is retained thereafter.

A qualifying completion is a matching completion for an assignment or tombstone whose provider is `anthropic`, purpose is `factory`, non-null proof `rollout_started_at` is no later than its `target_committed_at`, `consumer_class` is `production`, `provider_authenticated` is true and `alternate_credential_used` is false, independent of `legacy_pool_absent`. Its contribution identity is `consumer_run_id` plus `record_id`. If the matching completion marker already exists, `proof-update` MUST be a completed no-op and MUST NOT reapply any one-time or dated-soak rule. Otherwise the same atomic proof replacement MUST insert the marker with this completion's `completed_at` in canonical order and apply the remaining rules once. The first qualifying completion MUST set `production_success` only while that field is null; the first such completion carrying `legacy_pool_absent` true MUST likewise set `legacy_pool_absence_success` only while that field is null. Later qualifying completions MUST retain those first-writer values. A qualifying completion whose `completed_at` is not later than non-null `last_auth_failure_at` MUST NOT start, extend or replace the dated soak. Otherwise, the first qualifying completion after no current soak MUST set `successful_consumer_dates` to its UTC date and `soak_started_at` to `completed_at`; another on the latest recorded date MUST leave those fields unchanged; one on the next UTC date MUST append that date; one on a later nonconsecutive date MUST replace the dates with its date and set `soak_started_at` to its `completed_at`; and an out-of-order completion on an earlier date MUST not alter them. Only an authentication report for an assignment or tombstone whose provider is `anthropic`, purpose is `factory` and `target_committed_at` is at or after non-null `rollout_started_at` MUST set `last_auth_failure_at` to the later of its `occurred_at` and the stored value. It MUST clear `successful_consumer_dates` and `soak_started_at` exactly when no soak exists or its `occurred_at` is not earlier than `soak_started_at`; it MUST retain every completion marker, so replay of a completion applied before that failure cannot recreate cleared soak evidence. A late-arriving report about an event before the current soak MUST not clear it. Every other authentication report MUST leave the proof record unchanged. A qualifying authentication failure MUST NOT clear the one-time `simultaneous_spread`, `production_success` or `legacy_pool_absence_success` fields.

The seven-day proof MUST be complete exactly when `rollout_started_at` is non-null, the record contains at least seven consecutive dates and `soak_started_at` is non-null and later than `last_auth_failure_at`, unless `last_auth_failure_at` is null. This timestamp comparison permits a new qualifying soak to begin after a failure on the same UTC date. `proof-status` MUST derive `seven_day_complete` from that rule and the other three completion Booleans exactly from whether `rollout_started_at` is non-null and `simultaneous_spread`, `production_success` and `legacy_pool_absence_success` are non-null; all five Booleans, including `deprecation_ready`, MUST be false when `rollout_started_at` is null. The record MUST contain no credential or diagnostic. The deprecation decision MUST derive only from `deprecation_ready` computed from this record under spec.md §"LLM provider credential management"; a reader MUST NOT infer completion from logs or wall-clock waiting.

### Account-rotation separation

The published selection record from `caam-anthropic-loop` MUST remain the three-field, credential-free identity record defined above. `llm-provider-manager` MUST provision only independently validated credential material from its provisionable-token store and MUST NOT treat that identity record as a credential source.
