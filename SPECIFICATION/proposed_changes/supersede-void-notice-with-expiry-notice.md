## Proposal: Supersede activity-voiding with arm-until-idle and any-reason-death expiry-notice

### Target specification files

- SPECIFICATION/spec.md
- SPECIFICATION/scenarios.md

### Summary

Retire the activity-voided-ready model (a ready declaration voided when the session resumes work, answered by a once-per-round void-notice) and replace it with the arm-until-idle model already maintainer-directed for work-item overseer-xawpyl: a ready declaration is never voided by intervening narration or generation, remains armed until a verified settled-idle observation fires the restart, and is bounded only by a fixed max age. The obligation to notify the session when its declaration dies transfers from the retired void trigger to the new max-age-expiry trigger, keeping the same guarded-paste predicate, once-per-round durable bound, and state-file re-teaching content -- renamed from void-notice to expiry-notice.

### Motivation

Epic overseer-xkrwm3 (resume-submit-integrity), fronts 4-6, maintainer-directed 2026-08-16: work-item overseer-xawpyl implements arm-until-idle to fix a confabulation trap (three tracks, five consumed declarations, 2026-08-12..16) where activity-voiding destroyed legitimate ready declarations and left sessions to invent false completed-restart narratives. Its implementation (PR #1001) correctly removes the activity-voiding code path (void_if_stale becomes a no-op) but as shipped also deletes the void-notice mechanism entirely with no replacement, which would leave master's code silently non-compliant with the CURRENT ratified spec.md text (the void-notice MUST-rule at spec.md ~lines 264-280, shipped via Cluster B / PR #981 earlier the same session) the moment it merges. Maintainer ruling (relayed 2026-08-16): TRANSFER the notification obligation rather than drop it -- whenever the daemon lets a ready declaration die for ANY reason, it MUST send the session one notice; under arm-until-idle the only remaining death is max-age expiry, so this becomes an expiry-notice on that path. This proposal supersedes the spec letter to match that ruling BEFORE PR #1001 (to be amended to repurpose the notice machinery for expiry rather than delete it) is allowed to merge, per the epic's own merge-order requirement that master never hold a spec/behavior contradiction. Reading the current scenarios.md while drafting this proposal surfaced a SCOPE GAP beyond what the maintainer ruling explicitly named: two further scenarios ('A ready declaration is voided when its session resumes work' and 'Repeated voiding never re-sends an already-notified band', scenarios.md ~lines 182-207) ratify the activity-voiding trigger itself, not just its notice -- these are also directly contradicted by arm-until-idle and are included here for supersession so no latent mismatch remains after PR #1001 merges. Flagging this scope expansion explicitly for the independent reviewer and maintainer to confirm or narrow.

### Proposed Changes

In `SPECIFICATION/spec.md`, replace the paragraph beginning 'When a ready declaration is voided as stale inside a DELIVERED round, the daemon MUST send the session one VOID-NOTICE...' (ending '...The void-notice authorizes nothing.') with: A `ready` declaration is never voided by intervening session activity; the restart branch's own settle/busy/identity gates already prevent killing mid-work. A declaration remains armed until either a verified settled-idle observation authorizes the restart, or it exceeds a bounded maximum age, whichever comes first. When a declaration's maximum age is exceeded inside a DELIVERED round, the daemon MUST send the session one EXPIRY-NOTICE: a message stating that its ready declaration expired without a verified settled-idle observation, restating the exact state-file path and the three values it may write, and restating that a restart requires a fresh ready. The expiry-notice is subject to the complete guarded-paste predicate that governs a wrap-up, with one difference: its trigger is the expiry itself, not the below-threshold context trigger, so it MAY fire at any known context while its round remains open -- though a round closed as recovered before the notice lands sends no notice, the fresh round's own wrap-up re-teaching the protocol instead. The notice is sent at most ONCE per round however many expiries the round accumulates, and that bound is DURABLE alongside the round's notified bands, so a daemon restart never re-sends a notice already sent. The expiry-notice is a bounded companion to the escalation, not a band, and it MUST NOT re-open, re-fire, or reset any notified band. A failed expiry-notice paste MUST NOT un-open the round and MAY be retried on a later observation within the same round's single-notice bound. The expiry-notice authorizes nothing.

In `SPECIFICATION/scenarios.md`, replace the scenario 'A ready declaration is voided when its session resumes work' (Given a session that declared ready and then went busy again / When the declaration is older than the voiding grace / Then the daemon clears the now-false declaration instead of restarting later / And a declaration younger than the grace survives its own turn's busy tail / And the round's durable record survives the void / And the round's already-notified escalation bands are not reset) with: Given a session that declared ready and then went busy again / When the daemon next observes the track / Then the declaration remains armed and no restart occurs while the pane is not verified settled-idle / And the declaration is not cleared, voided, or otherwise altered by the activity / And the round's durable record and already-notified escalation bands are unaffected.

Replace the scenario 'Repeated voiding never re-sends an already-notified band' with a scenario reflecting that repeated activity never voids anything and therefore never re-sends anything -- OR, if the reviewer judges the case is now vacuous under arm-until-idle, remove it rather than retarget it (reviewer's call; noted here as an open question rather than resolved unilaterally).

Replace the scenario 'A voided ready declaration is answered with one durable bounded void-notice' (Given a delivered round in which a session's ready declaration was voided as stale / When the daemon next completes an observation whose guarded-paste predicate passes / Then the session receives one void-notice naming the state-file path and the fresh-ready requirement / And a second void within the same round sends no second notice, even across a daemon restart / And no notified escalation band is re-sent and no restart is authorized) with: '## Scenario: An expired ready declaration is answered with one durable bounded expiry-notice' -- Given a delivered round in which a session's ready declaration exceeded its maximum age / When the daemon next completes an observation whose guarded-paste predicate passes / Then the session receives one expiry-notice naming the state-file path and the fresh-ready requirement / And a second expiry within the same round sends no second notice, even across a daemon restart / And no notified escalation band is re-sent and no restart is authorized.

Reference implementation for the code side (already drafted, pending amendment per this supersession, NOT to be merged before this proposal ratifies): work-item overseer-xawpyl, PR #1001 in the livespec-overseer repository -- specifically its removal of maybe_send_void_notice and the *_notice_sent durable bound, which is to be repurposed (renamed, re-triggered on max-age expiry) rather than deleted.
